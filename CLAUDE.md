# WordPress-проект: ядро правил

## Язык — обязательное требование

Всё, что агент пишет и думает, — **только по-русски**: рассуждения, вопросы, уведомления, статусы, планы, отчёты, сообщения коммитов, тексты для хуков и скриптов.
Английский допустим только для имён в коде (функции, классы, переменные, CSS-классы, слаги), строк в `__()` до перевода, команд, путей и цитат из логов/ошибок.
Другой язык в ответе (в том числе из-за английского ввода, инструментов или скиллов) — нарушение; если получилось иначе, перейти на русский сразу.

Шаблон для работы Claude Code над WP-сайтами: прод и stage на сервере (SFTP/SSH), локальная копия. Cursor — только IDE для ручных правок и компиляции стилей.

## Область работы

- Код меняем только в **своих** темах, плагинах и mu-плагинах — слаги в `project-base/project.json`; границы держат хуки и `permissions`.
- Ядро (`wp-admin/`, `wp-includes/`, корневые `wp-*.php`), чужие плагины и родительскую тему не трогать — только хуки из своей темы или плагина. `wp-config.php` не в git.
- Клиентский сайт — правки в дочерней теме; свой плагин — только для переносимого функционала или по просьбе.
- Агент работает внутри проекта; всё вне его (ключи, личные файлы) — только через скрипты шаблона.

## Профиль и карта

- Профиль проекта (тип, стек, окружения, заливка, пакеты) — шапка `project-base/INDEX.md`. Стек бери оттуда, не определяй заново и не сканируй репо.
- Шапка из прочерков, а просят писать код → одной строкой предложи `project-init`, без уговоров.
- Остальное — по задаче: доступы `ACCESS.md` (читай до вопроса, не переспрашивай, новое пиши сразу); код — карта пакета → слой → md → исходник (правило `read-code`).
- Структурные правки (файл, функция, хук, класс добавлен / удалён / переименован) → обнови карту (skill `project-structure`); Stop-хук напомнит один раз.
- Архитектуру (FSE ↔ classic ↔ билдер) без явной просьбы не менять; выбор подхода — `project-init`.

## Рабочий цикл

- «Старт проекта» → skill `project-init`. Начало сессии — сверка с сервером до первой задачи (`project-base/WORKFLOW.md` → 2.1). Цикл, коммиты, откат — `WORKFLOW.md`.
- Сервер, сборка, наборы скиллов — только skill `project-ops`. Наборы — `skills-sync.mjs activate`, руками из `*-optional/` не копировать.
- После проверенной правки — коммит. Хронологию в markdown не вести — она в `git log`.

## Заливка и проверка

- **Код правится только локально.** На сервере файлы не пишем; на сервер — только `ssh-exec.mjs` (WP-CLI, чтение) и `sftp-sync.mjs`. Прямой `ssh` / `scp` / `sftp` запрещён.
- Режим заливки — `ACCESS.md` → «Заливка»; что делать в каждом режиме — правило `ops`.
- До «готово» — проверка в браузере (страница, консоль, сеть); вёрстка — правило `layout-check`. Отчёт `phpcs` / `stylelint` из хука исправляй.
- 3 неудачи подряд — стоп и вопрос пользователю. Пароли в ответах не цитировать.

## Безопасность

Правило `safety` (всегда в контексте). Хуки и настройки правит только человек, вручную; `deny` действует всегда.
`CLAUDE_TEMPLATE_DEV=1` при запуске `claude` отключает только проверки `guard-paths` и `guard-bash`.

## Решения

- Решения сайта — `project-base/DECISIONS.md`: читай перед архитектурной работой и при вопросе «почему так». Решения шаблона — `.claude/template/DECISIONS.md` (таблица «Действующие», журнал — по номеру).
- Принятому решению следуй. Считаешь ошибочным — скажи одной фразой и спроси, не переигрывай молча. Отброшенное не предлагай заново.
- Решение принято в диалоге → сразу запись (решение, причина, следствие, статус). Постоянные правила проекта — `INDEX.md` → «Правила проекта».

## Префикс проекта

Один `{stem}` на тему/плагин — в `project-base/project.json`. Свой код всегда с префиксом; чужой не переименовывать, оборачивать в свой блок.

| Слой | Форма | Пример при `stem = acme` |
|------|-------|--------------------------|
| SCSS / HTML / BEM | `{stem}-` | `.acme-hero`, `.acme-hero__title` |
| PHP (функции, хуки, константы) | `{stem}_` | `acme_enqueue_assets()` |
| JS | `{stem}` / `{stem}-` | `window.acme`, `acmeInit()` |
| Text domain / handle | `{stem}` или slug темы | `'acme'`, `acme-main` |

В репо уже устоявшийся другой префикс — используй его.

## Код

- Отступы **табами**, `tabSize` 4: PHP, SCSS, JS, HTML.
- PHP: WordPress Coding Standards, пробелы в скобках: `if ( $v )`, `foreach ( $a as $b )`.
- Escape: `esc_html()`, `esc_attr()`, `esc_url()`, `wp_kses()`. i18n: `__()`, `esc_html__()` с text-domain проекта.
- Картинки: `wp_get_attachment_image()`. Хуки вместо правок чужих плагинов/ядра.
- JS: ES6+, `defer` при enqueue, Vanilla, если проект не на jQuery.
- HTML5, семантика. Каркас секций — правило `markup-layout`.
- По-русски: комментарии, `project-base/`, коммиты. По-английски: имена в коде, слаги, строки в `__()` до перевода.

### Комментарии — обязательное требование

- Комментарий описывает **только то, что есть в коде сейчас**: что это или зачем нужно. Максимально коротко, одна строка, без рассуждений и оговорок.
- Про изменения — ни слова: не писать «удалил», «добавил», «заменил», «раньше было», «теперь», «исправлено», «потому что решили…». История правок — это `git log`.
- Не писать очевидное («Подключаем модуль», «Возвращаем результат») и не пересказывать код словами.
- Писать только: нестандартное решение, ограничение, костыль под чужой плагин, неочевидный порядок хуков, единицы измерения.
- Правишь код — комментарий приводи в соответствие коду; не оставляй устаревший и не дописывай рядом пояснение про правку.
- Многострочный блок — только шапка файла/секции и описание параметров миксина/функции. Секционные разделители — только в крупных entry-файлах.
- Docblock PHP — для публичных функций своей темы/плагина (`@param`, `@return`, короткое описание). `@version` в override-шаблонах Woo обязателен.

# Единообразие и актуальность (решения 059, 061)

## Типы записей (решение 061)

Всё решённое по типу записи (пост, проект, услуга, товар, любой CPT) — в своём файле `project-base/content-types/<post_type>.md`:
структура, поля, картинки, контент и тон, SEO, архив и таксономии, мелкие решения. Указатель — `content-types/README.md`. Заготовки — `project-base/_starter/content-types/`.

- **Читать только нужный файл.** Задача касается записи, шаблона, архива, картинок, текста или SEO типа X — прочитать `content-types/X.md` и делать по нему;
  файлы других типов не открывать и их решения на X не переносить. Тип неясен — по указателю.
- **Любое решение по типу — сразу в его файл**, в том же ходе: про картинки, тексты, SEO, поля, мелочи («анонс до 160 знаков», «без даты в slug»).
  Постоянное — в свой раздел, строкой в «Решения» — дата и причина. В `DECISIONS.md` проекта — только решения на весь сайт.
- **Первая оформленная запись типа** или смена оформления — файл из `_type.md` и строка в указателе; показать пользователю, после «да» — «Утверждено», коммит.
- **Добавляешь или правишь запись типа** — до работы прочитать файл, в конце сверить с образцом: порядок блоков, поля, картинки, `alt`, title, description, slug.
  Файла нет — сначала собрать по образцу, который назовёт пользователь, или по уже оформленной записи.
- **SEO-скиллы** (`seo-content`, `seo-schema`, `seo-page` и др.) по записи типа — сначала раздел «SEO» файла типа: его решения важнее общих советов скилла; новое согласованное — туда же.
- Структуру, где можно, закрепить в коде: паттерн, `template` у CPT, шаблон `single-<тип>` — по просьбе или в плане правки, не молча.
- Старые записи, оформленные иначе, — списком в «Расхождения», переделка — по просьбе.

## QA (решение 062)

Решения и отступления QA сайта (допуски, исключения, матрица страниц, согласованные расхождения с макетом) — `project-base/qa/QA.md`, сразу, в том же ходе.
«Не баг» — только с записью туда, иначе следующий прогон найдёт снова. Решение по типу записи — в файл типа, не в `QA.md`. Порядок — skill `qa` → п. 5.

## Один источник — правка везде

Меняешь значение, текст или фрагмент (телефон, адрес, почта, цена, ссылка, подпись, кусок разметки, размер, правило) — до «готово» найти все его копии:

- **Код и документы** — Grep старого значения по своим темам и плагинам, `markup/`, `project-base/` (паспорт, `content-types/`, карта, `INDEX.md`).
- **Контент сайта** — поиск по базе на сервере (WP-CLI, только чтение: `wp db search`, `wp post list --s=`); правка записей и опций — только списком и после «да» (правило `safety`).
- **Шаблон** — при правке правил шаблона: Grep по `.claude/`, `CLAUDE.md`, `project-base/WORKFLOW.md`.

В отчёте — «обновлено N мест» и что намеренно оставлено. Значение повторяется в двух и более местах кода — предложить один источник
(токен, опция, `template-part`, synced pattern, константа), не переделывать молча. Компоненты вёрстки — решение 056 (`site-design`, `layout-check`).

## Снимок — перепроверить перед действием

Строки хуков при старте, память, отчёты других сессий и прочитанное раньше — снимок на тот момент. Другой чат мог уже обновить шаблон, скиллы, ветку, сервер.
Перед тем как предлагать или делать действие над общим состоянием (обновление скиллов или шаблона, миграция, заливка, выкатка, смена ветки, правка записи) —
перечитать источник: файл (`.claude/template.json`, `skills.json`, `ACCESS.md`), `git status` / `git branch` / `git log -3`, сервер — `sftp-sync.mjs compare`.
Уже сделано — сказать одной строкой и не предлагать.

Обновление проекта до версии шаблона агент не предлагает — только по просьбе пользователя (`project-ops` → `template.md`).

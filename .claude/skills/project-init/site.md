# Этап 7. Сайт, браузер, админка, макет

Ответы — `ACCESS.md` → «Сайт и браузер», «Дизайн». Проверка в браузере обязательна — не спрашивать «проверять ли»; вопрос только если браузер не подключился.

## Агент выясняет сам

| Что | Откуда |
|-----|--------|
| публичный, stage и локальный URL | этапы 2–3 |
| адрес входа в админку | `/wp-admin`; перенесён плагином (WPS Hide Login и т.п.) — `wp option get` его настройки или страница плагина |
| доступ к БД | этап 3: WP-CLI есть → `wp db`; нет → вручную через панель |
| источник макета | этап 1 (вопросы о дизайне) — здесь только ссылка и подключение |
| ширины проверки | ширины макета или брейкпоинты стартера + брейкпоинты темы (ниже) |
| разрешённые домены браузера | прод, stage, локальный + CDN с первой загрузки главной (сетевые запросы) → пользователь подтверждает |

Домены — в `args` Playwright в `.mcp.json` (`--allowed-origins=<origin>;<origin>`, только схема + хост; флаг сверить по `npx -y @playwright/mcp@latest --help`).
Это не граница безопасности (не влияет на редиректы) — запрет сторонних сайтов держит правило `safety`.

## Спрашивается

### 1. «Создать агенту отдельного пользователя на сайте?»

Зачем: агент заходит на закрытые страницы и в админку для проверки — не под вашей учёткой и не под учёткой клиента.

| Окружение | Роль |
|-----------|------|
| локально, stage | администратор постоянно |
| прод | редактор; администратор — по задаче |

- Логин `claude-agent`, пароль длинный и уникальный на проект → `ACCESS.md` → «Пароль пользователя агента»; в чате не показывать.
- Создание: `wp user create claude-agent <почта> --role=<роль> --porcelain` — локально и на stage после «да», на проде после «да» с предупреждением.
  Без SSH — пользователь создаёт в админке.
- **Прод, повышение по задаче:** `wp user set-role claude-agent administrator` после «да» → задача → `wp user set-role claude-agent editor`. Оба действия — строкой в `audit.log`.
- **Админка — только просмотр:** не нажимать ничего, что сохраняет, удаляет, публикует, обновляет. Изменение — через WP-CLI (охранник, подтверждение, дамп);
  возможно только в админке — агент описывает шаги, нажимает человек.
- Вход в браузере: пароль агент вводит только на локальном сайте и на stage, который назвал пользователь; на проде под `claude-agent` входит человек
  (ограничение Claude) — один раз во встроенной панели, она хранит вход между сессиями. Админка и редактор — встроенная панель, вёрстка — Playwright `--isolated`;
  порядок — `layout-check` → «Редактор» (решение 050). Логин записать в `ACCESS.md` → «Пользователь агента» — пользователь уже есть на сайте под другим логином: записать его, не создавать второго.
- Двухфакторный вход для администраторов: агент коды не вводит — на проде остаётся редактором, или пользователь исключает его из 2FA только на stage.
- **До создания** проверить плагины безопасности (SiteGround Security, Wordfence, iThemes / Solid Security, Limit Login Attempts): принудительная 2FA для ролей,
  блокировка IP после неудачных входов, запрет новых администраторов. Настройки меняет человек; иначе агент заблокирует себе вход.
- Прод — рекомендовать журнал действий Simple History (клиент и вы видите, кто что делал).
- **При сдаче — удалить пользователя агента на проде** (`WORKFLOW.md` → 2.6).

### 2. Пароль на stage

Защита каталога на stage → `httpAuth` в `sftp-stage.json` (скрипты видят сайт, а не 401) и `.vscode/playwright-mcp.json` для браузера — **без пароля в адресе**
(`user:pass@host` запрещён правилами приватности): `project-ops` → `stage.md` → «Пароль stage». Не сработало — пользователь вводит пароль в окне браузера сам.

### 3. Figma

Макет в Figma (`да` / `создадим`) — ключ `figma` в `.mcp.json`, не затирая `playwright`:

```json
"figma": {
	"url": "https://mcp.figma.com/mcp"
}
```

Пользователю: `/mcp` → `figma` → Authenticate. Агент проверяет, что инструменты `figma` появились. Десктопный `127.0.0.1:3845` не предлагать без просьбы.
`создадим` — спросить **«В какой команде / проекте Figma создать файл?»** (зачем: файл появится там, где его увидит клиент) → `ACCESS.md` → «Команда / проект Figma»;
предупредить: запись на канвас требует Dev или Full seat на платном плане. URL файла агент запишет после `figma-create-new-file`.

## Брейкпоинты темы

Существующая тема — агент ищет сам (Grep по скачанному коду, WP-CLI — только чтение):

| Источник | Где |
|----------|-----|
| SCSS темы | переменные и миксины (`$breakpoints`, `@include media(...)`) |
| собранный CSS темы и плагинов вёрстки | все `@media (min-width / max-width: …)` — уникальные значения |
| `theme.json` (FSE) | `contentSize` / `wideSize` — ширины смены раскладки |
| билдер | Elementor: брейкпоинты в настройках сайта (`wp option get` настроек кита, чтение) |
| фреймворк темы | стандартные брейкпоинты Bootstrap / Tailwind |

Новая тема — брейкпоинты стартера и ширины макета; расходятся — сказать.
Результат — `INDEX.md` → «Профиль проекта» → «Брейкпоинты темы»; по ним правило `layout-check` проверяет каждую правку вёрстки.

## Скриншоты «до»

Существующие сайты (доработка, редизайн, переезд, SEO). Страницы — главная и страницы главных действий посетителя (этап 2).

- Ширины: каждый брейкпоинт темы **с обеих сторон** (768 → 767 и 768) + 375, 1440, 1920; значения ближе 20 px объединить.
- Во всю высоту; на каждой ширине — проверка горизонтальной прокрутки (`layout-check`).
- `project-base/screenshots/before/<страница>-<ширина>.jpg` — JPEG или сжатый PNG; в git — только ключевые страницы.
- Зачем: «как было до нас» и основа сравнения после правок — поехавшая вёрстка на нетронутой странице видна сразу.

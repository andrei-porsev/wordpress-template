# Старт проекта: опрос и настройка шаблона

## When to use

- «старт проекта», «новый проект», «настрой шаблон», «заполни описание проекта»
- Сразу после скачивания сайта с сервера, до первой правки кода

## Язык

Опрос, вопросы, уведомления и итоги — только по-русски (см. `CLAUDE.md` → «Язык»).

## Goal

Заполнить шапку `project-base/INDEX.md` и **все поля доступов** в `ACCESS.md`
(SFTP, SSH, WP-CLI, URL сайта, админка, браузер, Figma), применить слаги и префикс к конфигам.
Дальше агент не переспрашивает то же самое и не сканирует репозиторий.

---

## Порядок

### 0) Тип проекта — первый вопрос

До любых других вопросов — тип проекта: новый — нужен дизайн / новый — дизайн есть / клиентский — доработка / клиентский — редизайн.
Вопрос с вариантами, описания и маршрут каждого типа — [`types.md`](types.md).
Тип задаёт порядок блоков A–F, предзаполнение, что пропустить и стеки по умолчанию; дальше идти по маршруту типа,
общие правила блоков ниже действуют внутри него. Ответ — в `INDEX.md` → «Профиль проекта» → «Тип проекта».

### 0a) Анализ кода — сначала посмотреть, потом спрашивать

Для типов «доработка» и «редизайн», после `sync-down`. Новый проект — пропустить.
Не спрашивать то, что видно в коде. Перед вопросами определить самостоятельно:

| Что | Как определить |
|-----|----------------|
| Режим темы | `theme.json` + `templates/` → FSE; `header.php` → classic; активен Elementor/Bricks → builder |
| Активная тема | `style.css` темы, `Template:` в шапке → есть родительская |
| WooCommerce и ключевые плагины | список папок в `wp-content/plugins/` |
| Сборка | `package.json`, `webpack.config.js`, `src/` |
| Существующий SCSS | наличие `assets/scss/`, entry, `@use` или `@import` |
| Уже принятый префикс | имена функций в `functions.php` |

Найденное показать пользователю как **предзаполненные значения** и попросить
подтвердить или поправить.

Большой незнакомый репозиторий, а таблица выше ответа не дала — можно временно подключить стек `triage`
(`skills-sync.mjs activate triage`: `wordpress-router`, `wp-project-triage`), после старта — `deactivate triage`.
В работе над задачами они не нужны (решение 008).

### 1) Вопросы

Порядок блоков и что пропустить — по маршруту типа из [`types.md`](types.md), не по алфавиту.
Задавать блоками, а не по одному. Использовать вопросы с вариантами там, где
выбор дискретный. Ответ «не знаю» / «потом» — записывать прочерк, **не выдумывать**.

#### Формат вопроса — обязательно

Пользователь может не помнить, что за что отвечает. Каждый вопрос в чате:

- **Вопрос** + строка **«Зачем:»** — на что повлияет ответ, простыми словами, одно предложение.
  Описание ниже (после «—») — основа, пересказать коротко, не цитировать внутренние имена без пояснения.
- **Термин** (слаг, префикс, text-domain, mu-plugin, stage, `cwd`, `remotePath`) — пояснение в скобках и пример: «слаг темы (имя папки, например `acme-child`)».
- **Варианты** — у каждого описание «что будет при выборе» (поле `description` у вопроса с вариантами).
  Рекомендуемый — первым, с пометкой «(рекомендую)».
- Есть предзаполнение из п.0 — показать «нашёл: …, верно?».
- Блок начинать заголовком одной строкой: что за блок и зачем он целиком.

Пример:

> **Слаг папки темы?** (имя каталога в `wp-content/themes/`, например `acme-child`)
> Зачем: только эту папку агент будет править, заливать на сервер и хранить в git.

**Блок A. Проект** — что за сайт и какой объём работ; отсюда — какие инструменты подключить.
- Название и домен — подпись проекта и адрес для проверки сайта в браузере
- Что за сайт, для кого, ключевые сценарии пользователя — агент понимает, что важно не сломать и под кого делать
- Есть ли stage/dev-окружение или работа сразу на проде — stage (копия сайта для проверок) позволяет заливать правки без риска для живого сайта
- **Объём работ** (каждый пункт — стек, шаг 3.6; объяснять как «подключу инструменты для …»):
  - дизайн: рисуем в Figma с нуля / верстаем по готовому макету Figma / Claude Design (с нуля или готовый) / без макета → `figma` при первых двух, `design` — при Claude Design и без макета. Зачем: откуда агент берёт макет и размеры;
  - анимации: нужны сложные (сценарии при прокрутке, анимация текста) / только простые на CSS → `motion` при первом. Зачем: сложные требуют отдельной библиотеки и правил;
  - контент: пишем мы / даёт клиент / не наша задача → `content`, если пишем или правим мы. Зачем: инструменты для текстов и бриф;
  - SEO-аудит и сдача сайта (индексация, AI-видимость, скорость, доступность) → `seo` + `quality`. Зачем: проверки перед сдачей и доступы к Google-сервисам.
- Контент пишем мы — бриф для скиллов `content`, вопросы одним блоком: продукт и оффер, аудитория и её задачи,
  конкуренты (2–3 URL), тон и обращение («ты/вы»), язык сайта, что нельзя обещать. Ответы — в `.claude/product-marketing.md`
  (заголовки по вопросам, прочерк там, где ответа нет). Это файл, который скиллы `content` читают сами.
  Зачем (сказать пользователю): чтобы тексты были в одном тоне и без обещаний, которых нельзя давать.

**Блок B. Стек** (предзаполнить из п.0) — на чём сделан сайт; от этого зависит, как агент пишет код.
- Режим: FSE / classic / child к готовой теме / билдер (какой) — определяет, где живёт вёрстка: в блоках, PHP-шаблонах или билдере
- Тема и родительская тема — родительскую агент не правит, правки только в дочерней
- **Слаг папки темы** — имя каталога в `wp-content/themes/` (как в URL сайта).
  Обязательно: уйдёт в ignore и watcher SFTP/FTP. Не путать с человекочитаемым названием.
  Зачем: только эту папку агент правит, заливает и хранит в git
- WooCommerce: есть / нет, что продаётся — подключаются правила магазина (шаблоны, хуки корзины и оплаты)
- Ключевые сторонние плагины, которые определяют архитектуру (ACF, SEO, кеш, формы) — агент работает с ними через хуки и не правит их код
- Версии PHP и WP — какой синтаксис и функции можно использовать

**Блок C. Свой код** (слаги → `project-base/project.json`) — какие папки наши; только их агент правит и заливает.
- **Слаги своих плагинов** — имена каталогов в `wp-content/plugins/` (как в URL).
  Или «плагинов не будет». Обязательно: уйдут в ignore и watcher SFTP/FTP.
  Зачем: плагин нужен для функций, которые должны пережить смену темы
- **Слаги своих mu-plugins** — имена каталогов в `wp-content/mu-plugins/`.
  Или «mu-plugins не будет». Плейсхолдер `{mu-plugin-slug}`.
  Зачем: mu-plugin (включён всегда, отключить из админки нельзя) — для критичных мелочей
- **Слаг папки блока** `{block-slug}` — каталог в `plugins/<slug>/blocks/`
  (тот, у которого после сборки есть `style.css`). Нет блоков — прочерк.
  Зачем: агент знает, что собирать и заливать после правки блока
- Префикс `{stem}` для PHP/SCSS/JS — короткая метка (например `acme`) в именах функций и CSS-классов, чтобы не конфликтовать с чужим кодом
- Text-domain — идентификатор для перевода строк (обычно равен слагу темы)
- Куда пишем: child-тема / свой плагин / и то и то — куда по умолчанию класть новый код

**Блок D. Процессы** — что запускать после правок и когда задача считается сделанной.
- Сборка блоков (`@wordpress/scripts`) — будет или нет; при «да» агент после правки блока запускает `npm run build`
- Компиляция SCSS: Live Sass Compile или иное; где entry — откуда агент собирает CSS (entry — главный `.scss`-файл)
- Команды, которые нужно выполнять после правок — агент запускает их сам, не спрашивая каждый раз
- Критерий «задача выполнена»: что должно отработать без ошибок — по нему агент проверяет работу, прежде чем сказать «готово»

**Блок E. Ограничения** — чего агенту делать нельзя на этом проекте.
- Что трогать нельзя (чужой код, платные плагины, готовые шаблоны билдера) — агент обойдёт эти места стороной
- Отклонения от глобальных правил проекта (например «ACF-группы только через PHP») — правила этого проекта важнее общих
- Кто ещё правит сайт помимо вас — агент перед задачей проверяет чужие правки, чтобы их не затереть

**Блок F. Доступы** — обязательный, не пропускать и не сжимать до одной строки.
Читать и задавать по [`access.md`](access.md): SFTP (если ещё пусто), SSH и WP-CLI (все поля), сайт и браузер (URL, админка, проверка UI), Figma (файл, фреймы, MCP), Claude Design (F3b), БД,
SEO и аналитика (F6 — только при стеке `seo`).
Ответы сразу в `ACCESS.md` + `.vscode/ssh.json` / `sftp.json`. SSH = да — `ssh-exec.mjs test` в том же ходе.
Блок A уже дал домен — в F2 только подтвердить URL.

### 2) Записать ответы

`project-base/INDEX.md`, разделы шапки — строго по факту ответов:

- **Профиль проекта** — тип проекта, название, домен, назначение, дата; остальные поля профиля — по ответам, иначе прочерк
- **Профиль проекта → Стек** — режим, тема, плагины, префикс, text-domain, версии, сборка
- **Правила проекта** — только Блок E и отклонения. Общие стандарты из
  `CLAUDE.md` и `.claude/rules/` сюда **не** копировать
- **Команды** — из Блока D; если WP-CLI да — ещё вызовы `ssh-exec.mjs` из [`access.md`](access.md)
- **Обязательные проверки** — критерий из Блока D плюс браузер, если в F2 проверка = да
- **Важные моменты** — неочевидное из любого блока: где лежит логика, известные грабли

Доступы — **только** `ACCESS.md` и `.vscode/ssh.json` / `sftp.json`, не дублировать пароли в INDEX.
Блок F обязателен: пустой ACCESS после «старт проекта» — ошибка скилла, не «потом спросим».
Что записали — больше не спрашивать.

Незаполненное оставить прочерком — это честный сигнал «не выяснено».

Если в ходе опроса пользователь выбрал подход из нескольких вариантов или отказался
от чего-то по внешней причине — это уже решение: записать в `project-base/DECISIONS.md`
(решение, причина, следствие, статус), а в `INDEX.md` оставить только сухую формулировку.

### 3) Применить к конфигам

После записи ответов — не забыть, иначе настройки останутся шаблонными:

1. **Слаги и префикс — в `project-base/project.json`** (единственный источник):
   `stem`, `themes`, `plugins`, `muPlugins`, `blocks` (формат `"plugin-slug/block-slug"`).
   Родительскую тему не добавлять. Нет плагинов/mu-plugins/блоков — пустой массив.
2. **Сгенерировать whitelist:** `node .claude/skills/project-ops/scripts/gen-whitelist.mjs` —
   обновит `.gitignore` (между маркерами) и `.vscode/sftp.json` (`ignore`, `watcher`).
   Руками эти списки не править. Добавился плагин или блок — правка `project.json` и тот же запуск.
   `.vscode/sftp-ftp.json.example` — слаги в нём подставить руками; рабочий
   `.vscode/sftp-ftp.json` не трогать (секреты).
3. **Префикс.** `{stem}` уже в `project.json`; `CLAUDE.md` ссылается на него. В SCSS-заготовке
   `project-base/_starter/` заменить `cltm` на `{stem}` при переносе в тему/плагин.
4. `.vscode/settings.json` → `liveSassCompile.settings.includeItems` — путь к entry.
5. SCSS-заготовка: перенос по `project-base/_starter/README.md`; при конфликте имён зафиксировать
   неймспейс в «Правилах проекта».
6. **Стек: подключить скиллы и правила** одной командой, не копированием руками (решение 022):

   ```bash
   node .claude/skills/project-ops/scripts/skills-sync.mjs activate <стек…>
   ```

   Скрипт копирует скиллы из `.claude/skills-optional/` в `.claude/skills/`, парные правила из `.claude/rules-optional/`
   в `.claude/rules/` и записывает стеки в `.claude/skills.json` → `active`. Полный список — `skills-sync.mjs list`.

   | Ответ в опросе | Стек |
   |----------------|------|
   | FSE / block theme | `fse` (+ `interactivity`, если нужен интерактив на фронте) |
   | Classic / child | `classic` |
   | Билдер | `builder` |
   | Блоки на ACF / нативные блоки | `acf` / `blocks` |
   | WooCommerce | `woo` |
   | Свой плагин / REST API | `plugin` / `rest` |
   | **WP-CLI = да** (по итогам блока F1 / `ssh-exec.mjs test`) | `wpcli` — **обязательно** |
   | Дизайн в Figma или вёрстка по макету (блок A) | `figma` |
   | Дизайн в Claude Design или без макета (блок A) | `design` |
   | Сложные анимации (блок A) | `motion` |
   | Контент пишем мы (блок A) | `content` |
   | SEO-аудит и сдача (блок A) | `seo`, `quality` |
   | По запросу | `perf`, `phpstan`, `playground` |

   Стек с плагином (`seo`) — скрипт печатает фрагмент для `.claude/settings.json` и команды установки:
   отдать пользователю, сам `settings.json` не править. Ядро (`project-init`, `project-structure`, `project-ops`) скрипт не трогает.
   Сразу после — `skills-sync.mjs check`: устаревшие скиллы показать пользователю и обновить после «да» ([`skills.md`](../project-ops/skills.md)).
7. **Режим заливки** — `ACCESS.md` → «Режим заливки» (`guarded-auto` по умолчанию, `stage-auto`, `manual`).
   `stage-auto` — нужны `.vscode/sftp-stage.json` (и при других доступах `ssh-stage.json`) и Stage URL.
8. Доступы блока F — [`access.md`](access.md): `ACCESS.md`, `.vscode/ssh.json` / `sftp.json`, при необходимости `.mcp.json`. Не оставлять на «потом».

### 4) Окружение и проверка (вместе с пользователем)

Выполнять после шагов 1–3, по порядку. Что агент делает сам — делает; на шагах «спросить» останавливается и ждёт ответа.
Результат каждого пункта — одной строкой в чат и, где указано, в `ACCESS.md`.

1. **Node и зависимости.** `node -v` (нужен 20+; ниже — сказать, что обновить). Нет `.claude/skills/project-ops/node_modules` —
   `npm install --prefix .claude/skills/project-ops`.
2. **PHP для `php -l`.** `php -v`. Нет в PATH — поискать (`where.exe php`, типовые папки: `E:php-*`, OSPanel, XAMPP).
   Нашёл — **спросить**, добавить ли путь в PATH пользователем (агент системный PATH не меняет, даёт точную команду/шаги
   и просит перезапустить терминал). Не нашёл или отказ — записать в `ACCESS.md` → «Прочее»: «PHP локально: нет, `php -l` на сервере»
   (хук сам переключится на проверку на сервере).
3. **MCP.** Проверить наличие `mcp__playwright__*`. Нет — **попросить** пользователя выполнить `/mcp` и одобрить `playwright`
   (агент этого сделать не может); после ответа проверить снова. Figma — если в блоке F3 «да» или «создадим»: добавить `figma` в `.mcp.json`
   и попросить авторизацию через `/mcp`. Стек `seo` — проверить, что плагин `claude-seo` установлен (есть скилл `/seo`); нет — повторить пользователю
   команды из вывода `activate` и после установки предложить `/seo setup` (подключение Google API — F6).
4. **Хуки и охранники.** Если хуки не запущены — попросить одобрить проектные хуки (запрос при первом запуске / `/hooks`). Самопроверка,
   сервер и правки файлов не нужны (временный проект в системной temp):
   ```bash
   node .claude/hooks/selftest.mjs
   ```
   Ожидается «N из N прошли» и код выхода 0: проверяет `guard-paths`, `guard-bash`, `guard-wpcli`. Любой FAIL — остановиться и разобраться, дальше не идти.
   Сказать пользователю: права на правки файлов выданы (`acceptEdits`), границы держат хуки, журнал — `.claude/.state/audit.log`.
   Хуки и настройки защищены от правки агентом (`permissions.deny` и хуки); менять их человек может только вручную в редакторе.
4a. **Инструменты качества.** `stylelint` ставится тем же `npm install --prefix .claude/skills/project-ops` (конфиг `.stylelintrc.json`).
   `phpcs`: `phpcs --version` — есть ли, `phpcs -i` — стандарт WordPress. Нет — **спросить**, ставить ли
   (`composer global require --dev wp-coding-standards/wpcs dealerdirect/phpcodesniffer-composer-installer`; `phpcs.xml.dist` в корне уже есть).
   Отказ — записать в `ACCESS.md` → «Прочее»: «phpcs: нет»; хук просто пропустит проверку.
5. **Связь с сервером.** `sftp-sync.mjs test`; при SSH = да — `ssh-exec.mjs test`. Ошибки — без пароля в чате, доступы поправить в `ACCESS.md` и json.
6. **Режим заливки.** Напомнить выбранный режим и его цену (`guarded-auto` — правка сразу на живой сайт). Сайт с трафиком — предложить `stage-auto`.
   Режим `manual` — пункт 7 пропустить.
7. **Дымовой тест заливки** — только с явным «да» пользователя и **на stage, если он есть** (`stage-auto`); на проде — только если пользователь
   прямо разрешил. Тестовый файл в своей теме: `wp-content/themes/<slug>/claude-hook-test.php`.
   1. Создать файл с `<?php // hook test` (Write). Ожидается: хук залил, сайт HTTP 200. Проверить `sftp-sync.mjs fetch` или ответ сайта.
   2. Перезаписать файл с намеренной синтаксической ошибкой. Ожидается: хук вернул ошибку и откатил файл на сервере к версии из п.1
      (`php -l` локально до заливки или на сервере после).

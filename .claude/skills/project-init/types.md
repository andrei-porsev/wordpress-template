# Этап 1. Тип проекта

Первый вопрос инициализации. Тип задаёт порядок этапов, что пропустить, предзаполнение и стеки по умолчанию.
Формат вопросов — `SKILL.md` → «Формат вопроса». Ответ — `INDEX.md` → «Профиль проекта» → «Тип проекта».

## Вопросы

**1. «Сайт новый или уже существует?»**
Зачем: у нового сайта нет кода для анализа, у существующего сначала нужны доступы и копия.

**2а. Новый:**

| Вариант | Описание для пользователя |
|---------|---------------------------|
| нужен дизайн | макета нет: сначала рисуем дизайн, потом верстаем |
| дизайн есть | верстаем по готовому макету (Figma, Claude Design, файлы дизайнера) |

**2б. Существующий** (4 варианта — вопрос с вариантами):

| Вариант | Описание для пользователя |
|---------|---------------------------|
| доработка | правим и добавляем функции; внешний вид и архитектуру не меняем |
| редизайн | меняем внешний вид или тему целиком, сохраняя контент и адреса страниц |
| переезд | смена хостинга или домена |
| SEO и скорость | аудит и исправления без смены дизайна |

Редизайн — уточнение «нужен дизайн / дизайн есть», как у нового.

**3. Существующий — «Вы уже работали с этим сайтом?»**
Зачем: чужой код сначала разбираем и фиксируем, что было до нас.
- `да, знаю код` — сразу по маршруту;
- `нет, сайт после другого разработчика` — до маршрута аудит (этап 4 → «Полный аудит»).

Запись в профиль: `новый: нужен дизайн` / `новый: дизайн есть` / `доработка` / `редизайн: нужен дизайн` / `редизайн: дизайн есть` / `переезд` / `SEO и скорость`;
после другого разработчика — дописать `, после другого разработчика`.

## Маршруты

Номера — этапы `SKILL.md`. Этап 6 (пакеты) — у всех; этапы 8–10 — у всех.

| Тип | Порядок | Пропустить |
|-----|---------|------------|
| новый | 1 → 2 → 3 → (4 — только проверка безопасности, если WP уже стоит у клиента) → 5 → 6 → 7 → 8 → 9 → 10 | 4 — если WP ставим сами или сервера нет |
| доработка, редизайн, переезд, SEO и скорость | 1 → 3 → 4 → 2 → 5 → 6 → 7 → 8 → 9 → 10 | — |

У существующего этап 2 идёт после 4: данные о проекте уже найдены и только подтверждаются.
Полный бриф (`brief.md`) добирается сразу после этапа 6, если выбранный пакет его требует.

### Новый

- Сервера нет → в этапе 3 доступы прочерками, но **вопрос об окружениях задать** (локальная копия, stage на своём VPS).
  Ни сервера, ни локальной копии — строить и проверять сайт негде (проверка в браузере обязательна): предложить LocalWP (рекомендую) или stage на своём VPS.
  Режим — `manual`, с локальной копией — `local`; стек `playground` — по желанию.
- Сервер есть: «WordPress на хостинге уже стоит?» `да` / `нет, поставите вы` — агент ядро не ставит. Стоит у клиента — этап 4, только «Проверка безопасности» (чистый WP на чужом хостинге — не гарантия).
- Этап 5: FSE по умолчанию, тема своя; слаг, префикс, text-domain — из названия.
- **Нужен дизайн** — вопросы о дизайне (ниже), этапы «Сайт под ключ» (`WORKFLOW.md` → 1.4) все.
- **Дизайн есть** — вопросы о макете (ниже); в 1.4 бриф и структура — только если тексты пишем мы, дизайн-систему — из макета в `theme.json`, макеты не рисуем.

### Доработка

- Этап 5: стек из анализа, архитектуру не менять; дочерней темы нет → вопрос (`stack.md`).
- Этап 6: ничего не отмечено.
- Этап 7: дизайн по умолчанию «в стиле текущего сайта».
- Дальше — карта проекта (`project-structure`).

### Редизайн

После анализа (этап 4):

- **R1. «Глубина редизайна?»** Зачем: остаётся ли текущая тема или пишем новую.
  - `рестайл` — новый вид в текущей теме; архитектура та же.
  - `новая тема` — тема заново, контент и адреса сохраняются; режим по лестнице (`stack.md`); смена архитектуры — запись в `project-base/DECISIONS.md`.
    **С билдера на блоки** (Elementor → FSE): страницы, собранные в билдере, хранятся в его данных и в новой теме не отобразятся — контент пересобирается.
    Сказать пользователю цену, отметить пакет «Перенос контента»; адреса страниц сохранить (иначе — карта редиректов).
  - Рестайл на билдере или FSE — оговорка: глобальные стили живут в БД (набор Elementor Kit, `wp_global_styles` Site Editor), не в git и не выкатываются кодом.
    Билдер — экспорт / импорт набора Elementor на прод делает человек; FSE — стили держать в `theme.json`, не в редакторе сайта.
- **R2. «Где собираем новый вид до запуска?»** Зачем: живой сайт не должен ломаться, пока редизайн не готов.
  - `на stage (рекомендую)`;
  - `неактивной темой на проде` — только для новой темы;
  - `сразу на проде` — только для мелкого рестайла.
- Скриншоты «до» — обязательно (`site.md`); при пакете «Базовое SEO» — baseline `seo-drift`.
- Новая тема — новый слаг в `project.json` → `themes`; старую не добавлять. Читать её как образец: `sftp-sync.mjs download wp-content/themes/<старая>` —
  ляжет вне git (whitelist), править её не даст охранник; только после проверки безопасности.
- Пакеты «Базовое SEO» и «Скорость и доступность» отмечены по умолчанию.
- Переключение темы на проде — только по команде пользователя.

### Переезд

- Копию сайта и БД переносит человек: Duplicator, All-in-One WP Migration, WP Toolkit (Plesk), средства хостинга. Агент даёт шаги.
- Доступы к обоим серверам: старый — «Прод», новый — как stage (`sftp-stage.json` / `ssh-stage.json`) до переключения. Отдельный второй сервер — после части C плана.
- До переезда — скриншоты «до» и список адресов.
- До переключения: TTL DNS снизить заранее (человек, у регистратора); проверка безопасности старого сайта (этап 4) — заражение не переносим.
- После переноса: `search-replace` старого домена на новом сервере (`ssh-exec.mjs --stage -- wp search-replace … --dry-run`, потом «да»);
  чек-лист — HTTPS, редиректы, постоянные ссылки, формы, почта, cron, кеш; сравнение с «до».
- Смена домена: 301 со всех адресов старого домена, «Изменение адреса» в Search Console, карта сайта заново.
- **После переключения DNS** новый сервер становится продом: `stage-config.mjs promote` (план) → «да» → `promote --yes`
  (`sftp-stage.json` / `ssh-stage.json` → `sftp.json` / `ssh.json`, старые → `*.old.json`, снимок синхронизации — тоже);
  затем `ACCESS.md` → «Сервер», «Публичный URL», `gen-whitelist.mjs`, `connect-check.mjs`; режим заливки — по этапу 8 заново.
- Стеки: `wpcli`, `seo`. Вопросы о дизайне, анимациях, контенте — не задавать. «Базовое SEO» (адреса, редиректы) отмечено.

### SEO и скорость

- Сразу «SEO и аналитика» (`access.md` → раздел 5); перед правками — замеры «до».
- Стеки: `seo`, `quality`, `perf`. Дизайн и анимации — не спрашивать; контент — один вопрос «правим ли тексты».
- Пакеты «Базовое SEO» и «Скорость и доступность» включены.

## Вопросы о дизайне

Заменяют вопрос о дизайне в этапе 6 для типов «нужен дизайн» / «дизайн есть».

### Нужен дизайн

1. **«Где рисуем дизайн?»** Зачем: где агент создаёт макет и откуда потом верстает.
   - `Figma (рекомендую: макет показываем и утверждаем там)` — агент создаёт файл, дизайн-систему, макеты; нужен платный план с Dev или Full seat → стек `figma`, Figma = `создадим`;
   - `Claude Design` → стек `design`, Claude Design = `создадим`;
   - `без макета` — агент предлагает план (цвета, шрифты, сетка, раскладка), после «да» верстает → стек `design`.
2. Референсы и фирменный стиль — полный бриф (`brief.md`), ответы в `project-base/design/references.md`.
3. Какие страницы — из структуры (`brief.md`); тексты пишем мы — прочерк до этапа «Структура».

Утверждение своего макета — в Figma; запись `project-base/design/approved.md`: ссылка, имя версии из истории Figma, дата, что утверждено.
После утверждения — паспорт дизайна `project-base/design/system.md` по макету ([`design-system.md`](design-system.md)).

### Дизайн есть

1. **«В чём макет?»** Зачем: откуда агент берёт размеры, цвета, отступы.
   - `Figma` — ссылка → стек `figma`, Figma = `да`;
   - `Claude Design` → стек `design`, Claude Design = `да`;
   - `файлы` (PDF, картинки, XD, Sketch) — лёгкие в `project-base/design/client/`, тяжёлые — облачная папка; размеры по картинкам приблизительны, лучше попросить Figma → стек `design`.
2. **«Все ли страницы нарисованы?»** `все` / `ключевые, остальные по аналогии` / `не знаю`. Зачем: недостающие агент собирает из блоков макета, не придумывая стиль.
3. **«Какие ширины в макете?»** (например 375 / 768 / 1440). Зачем: под них проверяется вёрстка.
4. **«Есть ли UI-kit?»** (страница с цветами, шрифтами, кнопками). Зачем: при «да» переносим в `theme.json` один раз; при «нет» собираем из макетов и показываем на утверждение.

# Этап 5. Стек и свой код

Вместо технических вопросов («FSE / classic / билдер», «слаг») — вопросы о работе клиента и сайта; технику агент выводит сам.
Слаг темы, префикс, text-domain, версии PHP и WP — без вопросов, в сводку этапа 9 с пометкой ≈.

## Лестница выбора подхода

1. **FSE / block theme** — greenfield с нуля.
2. **Page builder + SCSS в child** — чужой стек (Elementor, Bricks…).
3. **Gutenberg-блоки на ACF** — гибкий контент без смены типа темы.
4. **ACF + PHP-шаблоны + SCSS** — classic / legacy.
5. **Хардкод в PHP** — точечно, не как архитектура.

Существующий сайт — архитектуру (FSE ↔ classic ↔ билдер) без явной просьбы не менять. `wordpress-router` и `detect_wp_project.mjs` не запускать.

## Новый сайт (и редизайн с новой темой)

**1. «Как клиент будет править сайт после сдачи?»**
Зачем: от этого зависит, на чём строить тему; переделать архитектуру потом — почти заново сделать сайт.

| Ответ | Стек |
|-------|------|
| меняет тексты и картинки в готовых секциях | FSE + блоки с полями (ACF) и заблокированные паттерны |
| сам собирает страницы из готовых секций | FSE + библиотека паттернов |
| хочет визуальный конструктор, двигать всё сам | билдер (Elementor / Bricks) + стили в дочерней теме |
| сам не правит, всё через нас | FSE |

Билдер — один раз назвать цену: сайт медленнее, тяжелее поддержка, клиент может сломать вёрстку. Решение за пользователем → `project-base/DECISIONS.md`.

**2. «Есть ли лицензия ACF Pro?»**
Зачем: блоки на ACF проще и быстрее, но требуют Pro.
- `да` → секции с полями на ACF (стек `acf`);
- `нет` → нативные блоки со сборкой (`blocks`, `@wordpress/scripts`).

Интерактив (фильтры, табы, калькуляторы) — нативные блоки всегда (`blocks`, `interactivity`).

**3. «Есть ли функции, которые должны пережить смену темы?»** (свои типы записей, CRM, расчёты)
Зачем: в теме они пропадут при её смене.
- `да` → плагин `{stem}-core` (стек `plugin`);
- `нет` → всё в теме.

mu-plugins и слаги блоков на старте не спрашивать: mu-plugin — когда понадобится, блок — в `project.json` при создании.

**4. Базовый набор плагинов** — [`plugin-sets.md`](plugin-sets.md) по виду сайта и посетителям. Пользователь правит список; установка — этап 9 (WP-CLI после «да»), если сайт уже стоит.

**5. Без вопросов:** слаг темы, префикс, text-domain — из названия (`Acme Studio` → `acme`); проверить, что слаг — допустимое имя папки.
PHP и WP — с сервера или «последние стабильные». Сборка — из стека: нативные блоки → `@wordpress/scripts`, SCSS → Live Sass в Cursor или `compile-scss`.

## Существующий сайт (доработка, SEO, переезд, рестайл)

Сводка найденного на этапе 4 и только:

1. **Дочерней темы нет** — «Создать дочернюю тему?»
   Зачем: правки в дочерней теме не слетают при обновлении основной.
   - `создать (рекомендую)` — тема из маркета или от другого разработчика;
   - `правим тему напрямую` — тема написана под этот сайт и не обновляется извне.
2. **Сайт на билдере** — «Новые секции делаем в билдере или кодом в теме?»
   Зачем: в билдере клиент правит сам; кодом — быстрее и легче, но правит только разработчик.
3. **Куда новый функционал** — агент рекомендует: дочерняя тема; свой плагин — для переносимого. Пользователь подтверждает.
4. **Сайт после другого разработчика — «Стили и скрипты: чей подход?»** По итогу `recon.md` → «Как работали с сайтом»; агент рекомендует вариант с причиной.
   Зачем: два параллельных подхода — лишние файлы и подключения, правки в двух местах, конфликты каскада.
   - `продолжаем их подход` — пишем туда же и так же (их файлы, их подключение, их сборка); правила шаблона `scss-bem` / `code-style` — только к тому, что пишем сами,
     линтеры чиним только в своих строках. Подходит, когда подход рабочий: стили в файлах темы, подключение через `wp_enqueue_*`;
   - `свой для нового, старое не трогаем` — новое по правилам шаблона (SCSS-заготовка, свои файлы по компонентам), старое живёт как есть, переносим только при правке;
   - `переводим на свой` — старое переносится в файлы темы по шаблону (код из базы и плагинов-вставок — тоже), лишние подключения убираем; это отдельная работа в плане, с оценкой.
   Код в базе (Additional CSS, сниппеты, шаблоны FSE из редактора) — при любом варианте назвать: в git его нет; перенос в файлы — по просьбе.
   Ответ — `INDEX.md` → «Стек» → «Стили и скрипты»; выбор с причиной — `project-base/DECISIONS.md` со ссылкой, от чего отступает («отступает от `scss-bem`, 029»).

## Стеки

| Ответ | Стек |
|-------|------|
| FSE | `fse` (+ `interactivity`, если интерактив) |
| classic / child | `classic` |
| билдер | `builder` |
| блоки на ACF / нативные | `acf` / `blocks` |
| магазин | `woo` |
| свой плагин / REST | `plugin` / `rest` |
| WP-CLI = да | `wpcli` — обязательно |
| по запросу | `perf`, `phpstan`, `playground` |

Стеки пакетов — `.claude/packages.json` (этап 6). Подключение — этап 9.

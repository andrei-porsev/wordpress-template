# Этап 3. Доступы и окружения

Ответы — в `ACCESS.md` → «Сервер», «Окружения». **Секреты — сразу** в `.vscode/sftp.json` / `ssh.json` (не в файл прогресса и не в чат);
в `ACCESS.md` — «в sftp.json» / «в ssh.json». Что уже заполнено — не переспрашивать, только подтвердить строкой.
«не знаю» / «потом» → прочерк. «нет» → `нет`, больше не спрашивать.

## 1. Хостинг и данные для входа

**1. «Какой хостинг?»** (IONOS, SiteGround, Hostinger, Bluehost, GoDaddy, Kinsta, WP Engine, Cloudways, свой VPS…)
Зачем: агент знает типичные настройки и предзаполнит порт, путь к сайту, наличие SSH и WP-CLI.

| Хостинг | Что ожидать |
|---------|-------------|
| Управляемый WP (Kinsta, WP Engine, Cloudways, SiteGround) | SSH и WP-CLI почти всегда; часто свой stage — предложить его. SiteGround: SSH и SFTP на порту 18765, **только по ключу** (пароль не принимает); путь `/home/customer/www/<домен>/public_html` |
| Shared (GoDaddy, Bluehost, Hostinger, IONOS) | SSH бывает выключен по умолчанию или ограничен; Hostinger: порт 65002. Подсказать, где включить |
| VPS (Hetzner, DigitalOcean, OVH, IONOS VPS) | всё есть; путь зависит от панели (Plesk: `/var/www/vhosts/<домен>/httpdocs`) |

**2. «Данные для входа»** — хост, логин, пароль или SSH-ключ. Можно вставить письмо хостинга или скрин панели — агент разберёт сам.
Пароль сразу в json, в ответе не повторять.

**3. Агент проверяет сам** (вопросов нет):

```bash
node .claude/skills/project-ops/scripts/install-deps.mjs
node .claude/skills/project-ops/scripts/connect-check.mjs [--stage]
```

`connect-check` проходит цепочку (раздел 2) и печатает итог: SSH да / нет, SFTP / FTP да / нет, WordPress в `remotePath` найден или нет,
WP-CLI, `php`, `find`, `md5sum` в оболочке (урезанная оболочка chroot — сказать), строку для `ACCESS.md` → «Подключение» и что из этого следует.
Ошибки — с диагнозом (таблица в разделе 3). Путь не тот — найти каталог с `wp-config.php` (`sftp-sync.mjs list <каталог>` по типичным путям хостинга) → `remotePath` / `cwd`.

Итог пользователю одной строкой: «SSH есть, WP-CLI есть, сайт в `/home/user/site.com/public_html` — верно?»

**Лимит: 2 неудачных входа подряд на хост — скрипты сами останавливаются** на 30 минут (`.claude/.state/auth-fails.json`): Fail2Ban (есть в Plesk) блокирует IP после нескольких ошибок.
Сброс — `connect-check.mjs --reset-auth`, только когда доступ исправлен. Вход с заведомо неверными данными «проверить» не пробовать.

**Ключ сервера** запоминается при первом входе (`.claude/.state/known-hosts.json`). Сменился — скрипты останавливаются до входа: назвать пользователю,
уточнить у хостинга (переустановка сервера или подмена); подтверждено — `connect-check.mjs --forget-host`.

## 2. Цепочка подключения

Пробовать по порядку, остановиться на первом рабочем:

1. **SSH + SFTP** — всё доступно.
2. **Только SFTP** — оболочки нет, передача файлов есть.
3. **FTPS** — FTP с шифрованием (`protocol: ftps`).
4. **FTP** — только с предупреждением: пароль идёт открытым текстом; предложить попросить у хостинга SFTP или FTPS.

FTP / FTPS — конфиг `.vscode/sftp-ftp.json` заполняет человек по `sftp-ftp.json.example` (агент файл не открывает)
и переключает на него скрипты: `.vscode/settings.json` → `"sftp.config": "sftp-ftp.json"`.

### Без SSH

Сказать пользователю простыми словами: «SSH нет, работаем по SFTP: заливка и откат будут, WP-CLI не будет — базу меняете вы».

- **Локальный PHP обязателен** — единственная проверка синтаксиса до заливки. Нет — предложить PHP из OSPanel или LocalWP (путь для PATH), этап 10.
- `debug.log` — скачать (`sftp-sync.mjs fetch wp-content/debug.log <локальный путь>`).
- Шаги с WP-CLI — ручная инструкция пользователю по `project-ops` → `no-wpcli.md` (замена домена, бэкап, пользователь агента, плагины…). После «готово» агент проверяет результат.
- `ACCESS.md`: `SSH → Есть: нет`, `WP-CLI: нет`, `БД → Доступ: вручную через панель хостинга`.

## 3. Помощник SSH

### Ключ — один раз на компьютер

- Проверить `~/.ssh/id_ed25519` (через скрипт или вопрос пользователю — агент вне проекта файлы не читает). Нет — предложить после «да»:
  `ssh-keygen -t ed25519 -f "$HOME/.ssh/id_ed25519" -N "" -C "<почта пользователя>"` (без парольной фразы — скрипты её не спросят; с фразой — записать её в `ssh.json` → `passphrase`).
- Ключ в формате PuTTY (`.ppk`) — скрипт не прочтёт; подсказать конвертацию в OpenSSH (PuTTYgen → Conversions → Export OpenSSH key).
- Приватный ключ остаётся на машине; в json — только `privateKeyPath`.

### Включить SSH на сервере — инструкция, делает человек

Агент на сервере ничего не меняет — даёт шаги и ждёт «готово».

**Свой VPS (Plesk на IONOS):**
1. Отдельная подписка на проект по плану «Stage» (`project-ops` → `plesk.md`) → свой системный пользователь; агент под `root` не ходит.
2. Подписка → «Доступ к веб-хостингу» → доступ по SSH: `/bin/bash` (план «Stage» ставит сам; в chrooted нет WP-CLI).
3. Публичный ключ — в `~/.ssh/authorized_keys` пользователя подписки: свой VPS — команда для SSH Terminal из `stage-config build` (ключ + PATH для PHP одной вставкой); иначе — SSH Keys подписки.
4. Порт SSH открыт в фаерволе Plesk **и** в облачном фаерволе панели IONOS.
5. WP-CLI в PATH пользователя — проверит `test`; нет — команда установки, выполняет человек.
6. После `/bin/bash` chroot снят и для SSH, и для SFTP: путь сайта — `/var/www/vhosts/<домен>/httpdocs` в `sftp.json` → `remotePath` и `ssh.json` → `cwd` (не `/httpdocs`).
   PHP Plesk не в PATH: человек пишет `export PATH=/opt/plesk/php/<версия>/bin:$PATH` в `~/.bashrc` (файла нет — создать, есть — строкой в начало; свой VPS — та же команда для SSH Terminal из `stage-config build`). Проверка — `ssh-exec.mjs -- wp core version`.

Доступ администратора Plesk агенту не даётся и в шаблоне не хранится.

**SiteGround:** Site Tools → Devs → SSH Keys Manager → Import — вставить публичный ключ (`id_ed25519.pub`); логин и хост — там же, в «SSH Credentials».

**Клиентский хостинг** — шаги под панель хостинга и **готовое письмо клиенту** (RU / EN по клиенту): «включите SSH и добавьте этот публичный ключ», с инструкцией под его хостинг.
Так не нужно просить у клиента пароль от хостинга.

### Диагностика

Скрипты (`connect.mjs`) сами дописывают диагноз к ошибке; таблица — то же для человека.

| Симптом | Вероятная причина | Что делать |
|---------|-------------------|------------|
| таймаут | порт закрыт фаерволом (Plesk, IONOS, хостинг) или не тот порт | проверить фаерволы, уточнить порт |
| `Connection refused` | SSH выключен | включить в панели |
| `Authentication failed` | не тот логин, ключ не добавлен, вход по паролю запрещён, права на `.ssh` | по шагам: логин → ключ в `authorized_keys` → права `700` / `600` |
| вошёл и выкинуло | оболочка `/bin/false` или chroot | Plesk: SSH → `/bin/bash` |
| `wp: command not found` | WP-CLI нет в PATH | путь к бинарю (`ssh.json` → `wpCli`) или установка |
| `php: not found` при `wp` | PHP панели не в PATH (Plesk: `/opt/plesk/php/<версия>/bin`) | человек: PATH в `~/.bashrc`; `wp` с префиксом `php` не запускать — `guard-wpcli` его не узнает |
| сверка: все файлы «удалены» | chroot снят, `remotePath` `/httpdocs` больше не существует | `/var/www/vhosts/<домен>/httpdocs` в `sftp.json` и `ssh.json` |
| сменился ключ сервера | переустановка сервера — или подмена | **стоп** (скрипты не входят), спросить пользователя; подтверждено — `connect-check.mjs --forget-host` |
| хост не найден | опечатка или DNS ещё не указывает на сервер | проверить адрес |
| ключ `.ppk` / зашифрован / `.pub` | формат PuTTY, нет `passphrase`, указан публичный ключ | конвертировать в OpenSSH, добавить фразу, указать приватный |

Ошибки — без пароля в чате.

## 4. Окружения

**«Какие окружения будут?»** (несколько вариантов) Зачем: куда агент заливает правки и где проверяет.
Задаётся всегда, даже без сервера (новый сайт — локальная копия или stage на своём VPS).

- `прод` — основной сайт (данные выше);
- `stage`: `у клиента` (данные как для прода → `sftp-stage.json` / `ssh-stage.json`) / `на моём VPS` / `нет`;
- `локально`: LocalWP / OSPanel.

**Stage на своём VPS.** Профиль VPS — `~/.wp-template/servers.json` (заполняет пользователь по `.claude/skills/project-ops/servers.example.json`, читает только скрипт):

```bash
node .claude/skills/project-ops/scripts/stage-config.mjs build <project>          # план
node .claude/skills/project-ops/scripts/stage-config.mjs build <project> --yes    # после «да»
```

Собирает `sftp-stage.json` и `ssh-stage.json`: хост, пользователь и URL — по шаблонам профиля (`{project}_dev`, `https://{project}.stage…`), `ignore` / `watcher` — из `sftp.json` проекта.
Вход по ключу (один ключ агента на все подписки) — пароль не нужен; по паролю — пароль подписки вписать в `sftp-stage.json`. Профиля нет — данные спросить как для stage у клиента.
Затем `connect-check.mjs --stage` и `ACCESS.md` → «Окружения», `Stage / dev URL`.
**Копию существующего сайта на stage — только после проверки безопасности** (этап 4, 🟢 или 🟡 без подозрительных файлов): здесь только отметить «будет stage»,
создание — в конце этапа 4. Создать stage — человек в Plesk по `project-ops` → `plesk.md` (подписка по плану «Stage», WP Toolkit: клон, импорт, установка + копия с локального сайта), агент ведёт по шагам; человеку — `/howto stage`.
После создания — чек-лист «безопасный stage» (`project-ops` → `stage.md`).

**Пароль на stage** (защита каталога) — свой у каждого проекта, его получает клиент: логин и пароль «Защищённые паролем папки» (не подписки и не FTP — так и сказать человеку) — в `sftp-stage.json` → `httpAuth` (в ответах не повторять), затем `stage-config.mjs auth <project>` — браузеру без пароля в адресе (`site.md`).
В `ACCESS.md` → «Окружения» — только где лежит и выдан ли клиенту.

**Локально** — процедура `project-ops` → `local.md`: копию делает человек (импорт архива в LocalWP, Duplicator в OSPanel),
затем `local-exec.mjs detect <корень WP>` → `.vscode/local.json`, `status`, при проекте отдельно от сайта — `link` (junction).
WP-CLI локального сайта — `local-exec.mjs -- wp …` (меняющее — с `--yes` после «да», с дампом). `ACCESS.md` → «Локально»: инструмент, URL, путь, `WP-CLI: local-exec.mjs`.

## 5. SEO и аналитика

Только при пакете «Базовое SEO» или типе «SEO и скорость». Ключи хранит плагин `claude-seo` (`/seo setup`), в `ACCESS.md` — факт и идентификаторы.

1. Search Console: сайт добавлен и подтверждён? `да` / `нет` / `добавим` → свойство (`sc-domain:…` / URL-префикс) и кто владелец. Зачем: индексация и запросы, по которым приходят.
2. GA4: ID ресурса или `нет`. Зачем: реальный трафик из поиска.
3. PageSpeed / CrUX: ключ Google API заводим? Зачем: скорость у реальных посетителей, а не только в тесте.
4. Картинки генерируем? (`/seo image-gen`, ключ Gemini). Зачем: превью для соцсетей и статей.
5. Bing Webmaster Tools: `да` / `нет`. Зачем: индексация в Bing → ответы Copilot.

«Да» по 1, 3, 4 — пользователь запускает `/seo setup` (агент ключи не вводит и не просит); после — `/seo google`, результат одной строкой в `ACCESS.md`.

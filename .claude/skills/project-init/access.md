# Этап 3. Доступы и окружения

Ответы — в `ACCESS.md` → «Сервер», «Окружения». **Секреты — сразу** в `.vscode/sftp.json` / `ssh.json` (не в файл прогресса и не в чат);
в `ACCESS.md` — «в sftp.json» / «в ssh.json». Что уже заполнено — не переспрашивать, только подтвердить строкой.
«не знаю» / «потом» → прочерк. «нет» → `нет`, больше не спрашивать.

## 1. Хостинг и данные для входа

**1. «Какой хостинг?»** (IONOS, SiteGround, Hostinger, Bluehost, GoDaddy, Kinsta, WP Engine, Cloudways, свой VPS…)
Зачем: агент знает типичные настройки и предзаполнит порт, путь к сайту, наличие SSH и WP-CLI.

| Хостинг | Что ожидать |
|---------|-------------|
| Управляемый WP (Kinsta, WP Engine, Cloudways, SiteGround) | SSH и WP-CLI почти всегда; часто свой stage — предложить его. SiteGround: SSH на порту 18765 |
| Shared (GoDaddy, Bluehost, Hostinger, IONOS) | SSH бывает выключен по умолчанию или ограничен; Hostinger: порт 65002. Подсказать, где включить |
| VPS (Hetzner, DigitalOcean, OVH, IONOS VPS) | всё есть; путь зависит от панели (Plesk: `/var/www/vhosts/<домен>/httpdocs`) |

**2. «Данные для входа»** — хост, логин, пароль или SSH-ключ. Можно вставить письмо хостинга или скрин панели — агент разберёт сам.
Пароль сразу в json, в ответе не повторять.

**3. Агент проверяет сам** (вопросов нет):

```bash
npm install --prefix .claude/skills/project-ops
node .claude/skills/project-ops/scripts/sftp-sync.mjs test
node .claude/skills/project-ops/scripts/ssh-exec.mjs test
```

- SSH с теми же данными работает → `Подключение: SSH + SFTP`;
- путь к WordPress — каталог с `wp-config.php` (`ssh-exec.mjs -- ls <каталог>` по типичным путям хостинга) → `cwd` и `remotePath`;
- WP-CLI — по выводу `test` (`WP-CLI:yes` / `WP-CLI:no`).

Итог пользователю одной строкой: «SSH есть, WP-CLI есть, сайт в `/home/user/site.com/public_html` — верно?»

**Лимит: не больше 2 неудачных попыток входа подряд.** На серверах с Fail2Ban (есть в Plesk) несколько ошибок блокируют IP — стоп и диагностика (раздел 3).

## 2. Цепочка подключения

Пробовать по порядку, остановиться на первом рабочем:

1. **SSH + SFTP** — всё доступно.
2. **Только SFTP** — оболочки нет, передача файлов есть.
3. **FTPS** — FTP с шифрованием (`protocol: ftps`).
4. **FTP** — только с предупреждением: пароль идёт открытым текстом; предложить попросить у хостинга SFTP или FTPS.

FTP / FTPS — конфиг `.vscode/sftp-ftp.json` заполняет человек по `sftp-ftp.json.example` (агент файл не открывает).

### Без SSH

Сказать пользователю простыми словами: «SSH нет, работаем по SFTP: заливка и откат будут, WP-CLI не будет — базу меняете вы».

- **Локальный PHP обязателен** — единственная проверка синтаксиса до заливки. Нет — предложить PHP из OSPanel или LocalWP (путь для PATH), этап 10.
- `debug.log` — скачать (`sftp-sync.mjs fetch wp-content/debug.log <локальный путь>`).
- Шаги с WP-CLI — ручная инструкция пользователю: замена домена — Better Search Replace; бэкап БД — панель хостинга или плагин; пользователь — админка. После «готово» агент проверяет результат в браузере.
- `ACCESS.md`: `SSH → Есть: нет`, `WP-CLI: нет`, `БД → Доступ: вручную через панель хостинга`.

## 3. Помощник SSH

### Ключ — один раз на компьютер

- Проверить `~/.ssh/id_ed25519` (через скрипт или вопрос пользователю — агент вне проекта файлы не читает). Нет — предложить после «да»:
  `ssh-keygen -t ed25519 -f "$HOME/.ssh/id_ed25519" -N "" -C "<почта пользователя>"` (без парольной фразы — скрипты её не спросят; с фразой — записать её в `ssh.json` → `passphrase`).
- Ключ в формате PuTTY (`.ppk`) — скрипт не прочтёт; подсказать конвертацию в OpenSSH (PuTTYgen → Conversions → Export OpenSSH key).
- Приватный ключ остаётся на машине; в json — только `privateKeyPath`.

### Включить SSH на сервере — инструкция, делает человек

Агент на сервере ничего не меняет — даёт шаги и ждёт «готово».

**Свой VPS (Plesk на IONOS):**
1. Отдельная подписка для stage → свой системный пользователь; агент под `root` не ходит.
2. Подписка → «Доступ к веб-хостингу» → доступ по SSH: `/bin/bash` (в chrooted часто нет WP-CLI).
3. Публичный ключ — в `~/.ssh/authorized_keys` пользователя подписки (расширение SSH Keys или файловый менеджер).
4. Порт SSH открыт в фаерволе Plesk **и** в облачном фаерволе панели IONOS.
5. WP-CLI в PATH пользователя — проверит `test`; нет — команда установки, выполняет человек.

Доступ администратора Plesk агенту не даётся и в шаблоне не хранится.

**Клиентский хостинг** — шаги под панель хостинга и **готовое письмо клиенту** (RU / EN по клиенту): «включите SSH и добавьте этот публичный ключ», с инструкцией под его хостинг.
Так не нужно просить у клиента пароль от хостинга.

### Диагностика

| Симптом | Вероятная причина | Что делать |
|---------|-------------------|------------|
| таймаут | порт закрыт фаерволом (Plesk, IONOS, хостинг) или не тот порт | проверить фаерволы, уточнить порт |
| `Connection refused` | SSH выключен | включить в панели |
| `Authentication failed` | не тот логин, ключ не добавлен, вход по паролю запрещён, права на `.ssh` | по шагам: логин → ключ в `authorized_keys` → права `700` / `600` |
| вошёл и выкинуло | оболочка `/bin/false` или chroot | Plesk: SSH → `/bin/bash` |
| `wp: command not found` | WP-CLI нет в PATH | путь к бинарю (`ssh.json` → `wpCli`) или установка |
| сменился ключ сервера | переустановка сервера — или подмена | **стоп**, спросить пользователя; не принимать новый ключ молча |

Ошибки — без пароля в чате.

## 4. Окружения

**«Какие окружения будут?»** (несколько вариантов) Зачем: куда агент заливает правки и где проверяет.

- `прод` — основной сайт (данные выше);
- `stage`: `у клиента` (данные как для прода → `sftp-stage.json` / `ssh-stage.json`) / `на моём VPS` / `нет`;
- `локально`: LocalWP / OSPanel.

**Stage на своём VPS.** Профиль VPS — `~/.wp-template/servers.json` (заполняет пользователь, читает только скрипт).
До части C плана (скрипт автосборки) — данные спросить как для stage у клиента. Создать stage — человек в Plesk (подписка, WP Toolkit: клон или импорт), агент даёт шаги.
После создания — чек-лист «безопасный stage» (этап 4, `recon.md`).

**Пароль на stage** (защита каталога) — логин и пароль в `ACCESS.md` → «Окружения»; браузеру — без пароля в адресе (`site.md`).

**Локально** — `ACCESS.md` → «Локально»: инструмент, локальный URL, путь, WP-CLI. Перенос сайта на локальный сервер — отдельная команда (`project-ops`, после части C);
до неё: копию делает человек (импорт архива в LocalWP, Duplicator в OSPanel), тема — junction из проекта:
`New-Item -ItemType Junction -Path "<сайт>\wp-content\themes\<slug>" -Target "<проект>\wp-content\themes\<slug>"` (после «да»).

## 5. SEO и аналитика

Только при пакете «Базовое SEO» или типе «SEO и скорость». Ключи хранит плагин `claude-seo` (`/seo setup`), в `ACCESS.md` — факт и идентификаторы.

1. Search Console: сайт добавлен и подтверждён? `да` / `нет` / `добавим` → свойство (`sc-domain:…` / URL-префикс) и кто владелец. Зачем: индексация и запросы, по которым приходят.
2. GA4: ID ресурса или `нет`. Зачем: реальный трафик из поиска.
3. PageSpeed / CrUX: ключ Google API заводим? Зачем: скорость у реальных посетителей, а не только в тесте.
4. Картинки генерируем? (`/seo image-gen`, ключ Gemini). Зачем: превью для соцсетей и статей.
5. Bing Webmaster Tools: `да` / `нет`. Зачем: индексация в Bing → ответы Copilot.

«Да» по 1, 3, 4 — пользователь запускает `/seo setup` (агент ключи не вводит и не просит); после — `/seo google`, результат одной строкой в `ACCESS.md`.

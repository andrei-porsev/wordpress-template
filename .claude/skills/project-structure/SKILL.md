# Иерархическая карта проекта (файл → функции)

## When to use

- Проект скачан с сервера, старт работы
- «построй/обнови структуру», «карта проекта», «опиши функции в …»

## Goal

Документация-навигатор:

1. **INDEX** — какой **пакет** (тема / свой плагин) и какой **слой** (фронт / бэк)
2. **INDEX пакета** — какой **файл/модуль** за что отвечает → ссылка глубже
3. **Файл детализации** — какая **функция / хук / класс / блок** за что отвечает
4. При необходимости ещё уровень (крупный класс → методы)

Рядом с картой — **инструкции слоя**: как править фронт или бэк *этого* пакета (точки сборки, куда класть новый файл, ограничения). Не копировать глобальные `.claude/rules/`.

Так проще искать код и меньше токенов на полный скан. Хронологию работ сюда **не** писать (для этого git / отдельные заметки пользователя).

## Layout

```
project-base/
  WORKFLOW.md                 # процедура работы: git, откат (не трогать при съёмке карты)
  INDEX.md                    # уровень 1: пакеты и слои
  DECISIONS.md
  _starter/                   # SCSS-заготовка, копируется в тему/плагин
  screenshots/                # скрины старого сайта при редизайне
  dumps/                      # дампы БД, в git
  themes/
    {theme-slug}/             # одна папка на свою тему, имя = слаг
      INDEX.md                # файлы этой темы по слоям + инструкции
      front/                  # витрина / стили / шаблоны / JS
        templates.md
      back/                   # PHP-логика / админка / хуки
        functions.md
    {another-theme}/
      …
  plugins/
    {plugin-slug}/            # одна папка на свой плагин, имя = слаг
      INDEX.md
      front/                  # вывод блоков, SCSS, viewScript
        blocks.md
      back/                   # регистрация, REST, админка
        admin.md
    {another-plugin}/
      …
```

Своих тем и своих плагинов может быть несколько — у каждого своя папка `{slug}/`.
Чужой parent и сторонние плагины не документировать.
mu-plugin — та же схема (`{slug}/front|back`), чаще только `back/`.

Внутри пакета — слои `front/` и `back/`, **только если слой есть**. Нет админки и PHP-логики — нет `back/`. Нет шаблонов, стилей и JS витрины — нет `front/`. Пустую папку не заводить.

Имена детальных файлов — стабильные, по смыслу модуля. Один исходный PHP → обычно один md (или группа мелких `inc/*.php` в одном md с якорными подзаголовками по файлу). Детальный md лежит **в папке своего слоя**.

### Что куда (слой)

| Фронт | Бэк |
|-------|-----|
| Шаблоны PHP/HTML, `template-parts/`, FSE `templates/` `parts/` `patterns/` | `functions.php`, `inc/`, классы плагина |
| SCSS/CSS, JS витрины | Админка, Settings API, ACF PHP/JSON групп |
| `theme.json` (стили и настройки оформления) | CPT, таксономии, REST, cron, письма |
| `render.php`, `viewScript`, стили блока | Регистрация блока, `register_block_type` |
| Woo overrides витрины (`theme/woocommerce/…`) | Woo-хуки логики (не шаблоны) |

Файл смешанный (типично `functions.php`): класть в **бэк**, во фронте — одна строка-ссылка («enqueue / поддержки темы — см. back/functions.md»), не дублировать таблицу символов.

Gutenberg-блок часто оба слоя: регистрация → `back/`, вывод и стили → `front/`.

## Ignore

Не документировать содержимое ядра WP, `vendor`, `node_modules`, uploads/cache, minified.  
Чужие плагины (Woo core, Elementor…) — в INDEX одна строка: не редактируем; без разбора их функций.  
`_starter/`, `dumps/`, `screenshots/` — не карта кода, в INDEX не разбирать.

Фокус: свои темы, свой SCSS/JS entry, `inc/`, overrides Woo в теме, свои плагины, ACF проекта.

## Сбор данных (без парсера)

Список файлов — **Glob** по теме и своим плагинам (`*.php`, `*.scss`, `block.json`).
Символы — **Grep** в этих путях:

```
^function |^class |add_action\s*\(|add_filter\s*\(
```

Имя ничего не говорит — **Read** куска файла (`offset` / `limit`). Итог — таблицы в md.

Не писать и не запускать: PHP/Node/Python-парсер, AST, `token_get_all`, `detect_*.mjs`, обход `Get-ChildItem` / `find`, временный JSON-индекс. Чтение исходников — rule `read-code`.

## Procedure

### 1) `project-base/INDEX.md` (уровень «пакеты»)

На русском. Шапка проекта — как раньше. Таблицы файлов сюда **не** тащить: они живут в INDEX темы/плагина.

```markdown
## Свои темы

| Тема | Слои | Детали |
|------|------|--------|
| `{theme-slug}` | фронт, бэк | [themes/{theme-slug}/](./themes/{theme-slug}/) |

## Свои плагины

| Плагин | Слои | Детали |
|--------|------|--------|
| `{plugin-slug}` | фронт, бэк | [plugins/{plugin-slug}/](./plugins/{plugin-slug}/) |
```

Нет слоя — не писать его в «Слои». Несколько пакетов — несколько строк.

### 2) INDEX пакета (уровень «файлы»)

`themes/{theme-slug}/INDEX.md` или `plugins/{plugin-slug}/INDEX.md`.

На русском:

```markdown
# Тема `theme-child`

Папка: `wp-content/themes/theme-child`

## Фронт

Инструкции (только это пакет/слой, не дубль `.claude/rules`):
- Entry SCSS: `assets/scss/index.scss`
- Новый компонент — партиал в `components/`, подключить в entry

| Путь | За что отвечает | Детали |
|------|-----------------|--------|
| `…/header.php` | Шапка витрины | [front/header.md](./front/header.md) |
| `…/assets/scss/index.scss` | Точка сборки стилей | кратко здесь или ссылка |

## Бэк

Инструкции:
- Новый хук — `inc/`, подключить из `functions.php`

| Путь | За что отвечает | Детали |
|------|-----------------|--------|
| `…/functions.php` | Подключает inc, тему, хуки | [back/functions.md](./back/functions.md) |
```

Слоя нет — секции нет, папки нет. Не писать «Фронт: отсутствует».

Правила:

- Каждая важная точка входа — строка: **путь → ответственность → ссылка** (если есть разбор глубже)
- Мелкие/очевидные файлы можно описать только в таблице INDEX без отдельного md
- **Инструкции** — 2–6 пуль: куда класть новое, чем собирать, чего не трогать *в этом слое этого пакета*. Глобальные стандарты (WPCS, BEM, escape) сюда не копировать
- Нечего сказать сверх правил — прочерк, пустой `instructions.md` не заводить
- Без вставки тел кода

Отдельный файл `front/instructions.md` / `back/instructions.md` — только если инструкций больше, чем уместно в INDEX (длинный чеклист сборки, карта партиалов). Иначе держать в секции INDEX.

### 3) Детальный md (уровень «функции»)

Для файла вроде `functions.php` / `inc/woo.php` — в `back/` (или `front/` по слою):

```markdown
# `wp-content/themes/…/functions.php`

Кратко: роль файла в целом.

## Символы

| Имя | Тип | За что отвечает |
|-----|-----|-----------------|
| `cltm_setup` | функция | after_setup_theme: поддержки темы |
| `cltm_enqueue_assets` | функция | стили/скрипты фронта |
| `woocommerce_before_main_content` | хук (remove/add) | … |
```

Допустимо:

- Группировка по секциям (Setup / Assets / Woo / Ajax)
- Для класса — таблица методов тем же форматом
- Указать номер строки *примерно*, если файл огромный и это реально помогает (опционально)

Нельзя:

- Копировать реализацию функции целиком
- Расписывать чужой код плагинов

### 4) Глубина

- Сначала INDEX пакета по всем ключевым файлам, разложенным по слоям
- Детальные md — для файлов с несколькими функциями/хуками или неочевидной логикой
- Один «бог-файл» на 50 функций — один md с таблицей, не 50 файлов
- Корневой `project-base/INDEX.md` — только пакеты и ссылки, без полного списка файлов

### 5) Обновление

- Изменился набор функций в файле → обновить его md и при необходимости строку в INDEX пакета
- Новый важный файл → строка в нужном слое INDEX пакета + md при необходимости
- Появился или исчез слой (был только бэк, добавили SCSS) — создать/убрать папку слоя и поправить «Слои» в корневом INDEX
- Не переписывать всю карту ради одной правки

### 6) After write

Сообщить: какие пакеты, какие слои, сколько файлов в INDEX пакетов, какие детальные md созданы.  
В следующих задачах: корневой INDEX → INDEX пакета → слой → уже точечный Read исходника.

## Verify

- [ ] Корневой INDEX: каждая своя тема и каждый свой плагин — строка со слоями и ссылкой на `{slug}/`
- [ ] INDEX каждого пакета лежит в `themes/{slug}/` или `plugins/{slug}/`; файлы по фронт/бэк; пустого слоя нет
- [ ] Инструкции слоя — только своё пакета, без копипаста `.claude/rules/`
- [ ] Детальные md лежат в `front/` или `back/` своего пакета: функции/хуки/классы с ролями на русском
- [ ] Нет простыней кода и разбора чужих плагинов
- [ ] Можно пройти путь «нужна фича X» → пакет → слой → файл → функция без полного скана репо
- [ ] В репозитории не появилось парсера / скрипта обхода / JSON-индекса исходников

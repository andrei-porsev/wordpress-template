# Обновление проекта до версии шаблона

Шаблон — **только с GitHub** (решение 032): скрипт проекта клонирует его по `.claude/template/manifest.json` → `repo` во временную папку
и запускает свежую версию себя оттуда; локальная папка шаблона и путь к ней не нужны. Метка версии проекта — `.claude/template.json` (пишет скрипт).

```bash
node .claude/skills/project-ops/scripts/template-update.mjs .            # пробный прогон, ничего не меняет; коммит шаблона запоминается
node .claude/skills/project-ops/scripts/template-update.mjs . --apply    # после «да» — ровно показанный коммит
```

Запуск — из папки проекта. Нет доступа к `repo` (сеть, приватный форк без входа) — скрипт скажет «шаблон не скачан»: назвать причину пользователю, обходных путей не искать.
Скрипт в проекте старый, без запуска с GitHub (проект на версии до 2026.11.20.5): один раз — скрипт из любой свежей копии шаблона с путём проекта аргументом
(`node "<копия>/.claude/skills/project-ops/scripts/template-update.mjs" "<проект>"`): он тоже берёт шаблон с GitHub; после `--apply` в проекте — новый скрипт.
`--local` — только автору шаблона: пробный прогон по его папке шаблона до пуша (`--worktree` — с незакоммиченным); применять так нельзя.

## Когда

- **Только по просьбе пользователя** — отдельная операция, когда он сочтёт нужным (решение 059). Агент обновление не предлагает и о новых версиях шаблона не напоминает.
- При старте сессии хук сообщает только о начатом и не доведённом обновлении: незавершённая миграция (шаг 5), нерешённые конфликты (шаг 4),
  невлитая ветка `template-update` (шаг 9). Это состояние, а не повод обновлять заново: доделать — по просьбе.
- Перед пробным прогоном и `--apply` — состояние перечитать: `.claude/template.json`, `git branch`, `git status` (могли обновить в другом чате, правило `safety` → «Снимок»).
  Пробный прогон печатает «Проект уже на версии X» — обновлять нечего, сказать одной строкой.

## Процедура

1. **До обновления:** в проекте всё закоммичено; сверка с сервером (`sftp-sync.mjs compare`) — отличий нет или скачаны и закоммичены (на проде источник правды — сервер).
   Прода нет (пустой host в `sftp.json`), есть stage — сверка со stage (`compare --stage`); нет ни того, ни другого — пропустить и сказать одной строкой.
   В старом `sftp-sync.mjs` нет `compare` — `sync-down` (только свой whitelist) и `git status`; разница только в переводах строк (`git diff --ignore-all-space --ignore-cr-at-eol` пуст) — `git restore`, не коммитить.
   Состояние git (`remote`, ветки) — проверять командой (`git remote -v`), не по догадке.
2. **Пробный прогон** — показать пользователю отчёт: заменить / добавить / удалить / объединить / конфликты, стеки скиллов, защищённые файлы, миграции.
   Раздел «сторонние скиллы» — подключённые скиллы, у которых в шаблоне новая закреплённая версия: какие файлы изменятся и что нашла проверка.
   Разобрать для пользователя по сути (что поменялось в инструкциях, безопасно ли); находки «НЕ принимались в шаблоне» — назвать отдельно.
   «ВНИМАНИЕ: после поднятия версии X в шаблоне ещё коммитов» — сначала поднять версию в шаблоне (`manifest.json`), коммит, затем прогон заново:
   иначе проект получит правки под старой меткой, и следующее обновление их не отличит.
   Метку новый проект получает в `project-init` (`--init-label`: версия, с которой создан, и её коммит в шаблоне), от неё и считается обновление.
   Проект без метки (перенесён до этого): опора — коммит, где появился `.claude/settings.json` (иначе `--base <коммит>`). Вне `.claude/` вписанное при переносе считается правкой проекта:
   предок — совпавшая или ближайшая версия шаблона; версии на переносе нет в истории — конфликт «сравнить с шаблоном» (решение 036).
3. **«Да» → `--apply`:** применяется коммит шаблона из пробного прогона, даже если в шаблон с тех пор что-то запушили (без пробного прогона — отказ).
   Тег `before-template-update-<версия>`, ветка `template-update`, бесконфликтное применяется, метка, коммит.
   Затем сторонние скиллы — `skills-sync.mjs install` ставит закреплённые версии (сверка `hash`, проверка), отдельный коммит.
   Не подключился из-за новых находок — показать их пользователю; после его «да» — `install <имена> --accept`, коммит.
4. **Конфликты** — по каждому показать разницу и решить с пользователем:
   `--take template <путь>` (взять шаблонный) · `--take project <путь>` (оставить проектный) · `--take merge <путь>` (маркеры `<<<<<<<` → поправить → `--take project <путь>`).
   `template` и `project` коммитят файл и метку сами.
   `.gitattributes` — предложить шаблонный (`* text=auto eol=lf` покрывает правила проекта по расширениям), затем `git add --renormalize .`; изменилось — отдельный коммит.
5. **Миграции:** инструкция из отчёта (`.claude/template/migrations/<версия>.md`) — по шагам, с показом разницы, коммиты; затем `--done <версия>` (метку коммитит сам).
6. **Хуки и `settings.json` — человек** в своём терминале: готовую команду с путями печатает `--apply` — отдать её пользователю как есть, блоком кода
   (скрипт сам спрашивает y/n; агент эту команду не запускает).
   Опору хуков до обновления `--apply` хранит в метке (`protectedBase`); после применения агент сверяет хуки и `settings.json` с шаблоном.
   `--take` и `--protected` берут шаблон на коммите из метки — тот же, что применён.
   Ожидающие правки настроек самого шаблона — забота автора шаблона: `… . --protected` в его папке шаблона, коммит, пуш.
7. **Проверка:** перезапуск Claude Code в проекте → `node .claude/skills/project-ops/scripts/install-deps.mjs` (зависимости скриптов могли измениться),
   `gen-whitelist.mjs` (entry SCSS из `project.json` → `scss`; поля нет — сначала вписать туда путь из `includeItems` ветки `main`), `node .claude/hooks/selftest.mjs`, `connect-check.mjs`, сайт в браузере; режим заливки авто — пробная безвредная правка в теме (комментарий) и проверка, что хук залил и сайт жив.
8. **Доинициализация:** `project-init`, повторный запуск — только поля-прочерки профиля.
9. Пользователь смотрит итог и сливает `template-update` в основную ветку, пуш. Откат — `git checkout main && git branch -D template-update` (тег остаётся).

## Что скрипт не трогает

Проектные файлы (`ACCESS.md`, `project.json`, карты, решения проекта, `.vscode/sftp*.json`, `ssh*.json`, `wp-content/`) — только механика миграций.
`settings.local.json`, `.claude/.state/`. Хуки и `settings.json` — только в `--protected`. Планы шаблона (`project-base/plans/`) в проекты не попадают.
Подключённые правила и свои скиллы шаблона (`.claude/rules/<стек>.md`, `.claude/skills/<свой скилл>`) обновляются из `*-optional` шаблона;
сторонние скиллы — скачиванием закреплённой версии (решение 016), копию с правками проекта скрипт не трогает и называет в отчёте.
Стеки — из `skills.json` → `active`, у проекта без манифеста — по составу подключённых копий.

## История шаблона переписана

Метка проекта хранит хеши коммитов шаблона: по ним `template-update` берёт предка для слияния. После переписывания истории шаблона (`git filter-branch` / `filter-repo`)
старые хеши исчезают — до следующего обновления каждому подключённому проекту:

```bash
node .claude/skills/project-ops/scripts/template-update.mjs . --remap <таблица «старый новый»>
```

Скрипт меняет хеши в `.claude/template.json` (`commit`, `protected`, `protectedBase`, `unresolved`) и коммитит метку; затем пробный прогон — без лишних конфликтов.
Хеш не найден ни в таблице, ни в шаблоне — предупреждение: предок будет запасной (файл проекта на опоре).

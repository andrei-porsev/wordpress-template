# Локальная копия сайта (LocalWP, OSPanel)

Когда: сайт ведёт себя по-разному на серверах, нужна отладка или доработка без риска для живого сайта. Команда пользователя — «перенеси сайт локально».
Локальная копия — третье окружение рядом с продом и stage; готовое уходит на прод выкаткой (`sftp.md` → `deploy`).

## 0. Сначала — сравнение окружений

Часто перенос не нужен: причина — разница окружений. `recon.mjs` (и `--stage`) → `recon.mjs --env-table`: отличия версий WordPress, PHP, веб-сервера, кеша выделены.

## 1. Копия сайта — человек

Скрипты шаблона качают только свой код, весь сайт и БД переносит человек:

- **LocalWP:** на сервере — экспорт All-in-One WP Migration или Duplicator (или бэкап хостинга) → в LocalWP перетащить архив (Import site).
- **OSPanel:** Duplicator — `installer.php` + архив в папку домена OSPanel, открыть установщик в браузере.

Агент даёт шаги и ждёт «готово». Перед этим — проверка безопасности прода (`project-init` → `recon.md`): заражённое на машину не переносим.

## 2. Подключить локальный сайт

```bash
node .claude/skills/project-ops/scripts/local-exec.mjs detect "<корень WP локального сайта>"   # план
node .claude/skills/project-ops/scripts/local-exec.mjs detect "<корень WP>" --yes             # .vscode/local.json
node .claude/skills/project-ops/scripts/local-exec.mjs status
```

`detect` находит сам: LocalWP — по `local-site.json` (PHP сайта, порт БД, клиент MariaDB / MySQL, адрес), OSPanel — PHP из модулей, БД 3306; `wp-cli.phar` — в корне сайта или в LocalWP.
`status` — работает ли PHP, запущена ли база, отвечает ли сайт; не так — строка «СДЕЛАТЬ ВРУЧНУЮ» (запустить сайт в LocalWP, OSPanel, скачать `wp-cli.phar`).
Записать в `ACCESS.md` → «Локально»: инструмент, URL, путь, `WP-CLI: local-exec.mjs`.

**Раскладка:**

| Проект | Что делать |
|--------|------------|
| внутри папки сайта (корень проекта = корень WP, как у LocalWP-сайта с шаблоном внутри) | ничего — сайт видит код напрямую |
| отдельно от сайта | `local-exec.mjs link` (план) → «да» → `link --yes`: junction своих тем / плагинов из `project.json` в сайт. В сайте уже настоящая папка — стоп, переименовать или удалить её — человек, после сверки |

## 3. Подготовить копию

Через `local-exec.mjs -- wp …` — изменения после «да» пользователя (`--yes`), перед каждым — дамп в `.claude/.state/local-backup-*.sql`:

1. Домен: `wp search-replace '<прод>' '<локальный>' --dry-run`, затем без `--dry-run` с `--yes`.
2. Почта: плагин-заглушка (LocalWP перехватывает письма сам — Mailpit).
3. Кеш и CDN: отключить плагины кеша / CDN.
4. Woo: тестовые ключи оплаты (ввод ключей — человек).
5. Отладка: `WP_DEBUG` / `WP_DEBUG_LOG` в `wp-config.php` — человек (агент `wp-config` не читает и не правит).

## 4. Работа и выкатка

- Режим заливки — `manual (local)` (`ACCESS.md`): хук не знает режима `local` и без `manual` в начале зальёт на прод.
- Проверка в браузере — по локальному URL.
- **Переносится только код.** Настройки, сделанные в локальной админке (опции, меню, ACF), на прод не уедут — держать их в коде (ACF JSON, `theme.json`) или перечислить для ручного повтора.
- На прод — `sftp-sync.mjs deploy` (план) → «да» → `deploy --yes`.

## Защита `local-exec`

| Команда | Что будет |
|---------|-----------|
| чтение (`list`, `get`, `status`, `--dry-run`, `db query SELECT`…) | сразу |
| меняющее (`option update`, `plugin activate`, `search-replace` без `--dry-run`, `eval`…) | только с `--yes` после «да»; перед — дамп БД |
| `db drop` / `reset` / `clean`, `site empty` / `delete` | запрещено |
| не WP-CLI | не выполняется |

Полная защита охранником `guard-wpcli`, как для `ssh-exec`, — часть D плана (правка хука, человек).

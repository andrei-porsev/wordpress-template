# Процедура работы над проектом

Шаблон универсальный. Этот файл — что сделать при старте конкретного проекта
и как вести работу, чтобы в любой момент можно было понять историю и откатиться.

Разработка идёт **на сервере** (SFTP), поэтому git здесь — не «хранилище кода»,
а единственный способ узнать, что и когда менялось на живом сайте.

---

## 1. Старт проекта

### 1.1. Настроить шаблон под проект

Команда агенту **«старт проекта»** — skill `project-init` ведёт опрос по 10 этапам с ветвлением по типу проекта
(новый: нужен дизайн / дизайн есть; существующий: доработка / редизайн / переезд / SEO и скорость), показывает одну сводку
и после «да» записывает профиль в `INDEX.md`, `ACCESS.md`, `project.json`, подключает наборы скиллов. Изменить настройки позже — «поменяй настройки проекта».
Ниже — что делается по шагам (для ручного прохода и понимания).

1. Доступы и окружения — `project-init` → `access.md`: хостинг, данные для входа (секреты сразу в `.vscode/ssh.json` / `sftp.json`), проверка SSH, SFTP, WP-CLI, stage, локальная копия.
   Операции потом — skill `project-ops` (`sftp.md`, `ssh.md`). Что в ACCESS заполнено — не переспрашивать.
2. Существующий сайт — разведка и проверка безопасности **до скачивания** (`project-init` → `recon.md`), затем 1.2.
3. Слаги темы, своих плагинов, mu-плагинов, блоков и префикс `{stem}` — в `project-base/project.json`.
   Затем `node .claude/skills/project-ops/scripts/gen-whitelist.mjs`: обновит whitelist в `.gitignore`
   и `ignore` / `watcher` в `.vscode/sftp.json`. Родительскую тему не добавлять.
4. Скиллы и правила под стек и пакеты — `node .claude/skills/project-ops/scripts/skills-sync.mjs activate <стек…>`
   (таблица в `project-init` → `stack.md`, пакеты — `.claude/packages.json`; WP-CLI = да → обязательно `wpcli`), затем `check` — обновить устаревшее.
   Подробно — `project-ops` → `skills.md`, решение 022. Ядро: `project-init`, `project-structure`, `project-ops`.
5. Режим заливки в `ACCESS.md`: `guarded-auto` / `stage-auto` / `manual` (локальная копия — `manual (local)`).
6. Окружение и проверка (Node, зависимости, PHP, MCP, хуки, связь, тест заливки) — `project-init` → `SKILL.md` → этап 10, агент ведёт сам.
7. Перенести SCSS-заготовку в тему/плагин по инструкции `project-base/_starter/README.md`.
   Проект с нуля — папка `scss/` целиком; в проекте уже есть SCSS — только
   `abstracts/`, предварительно проверив конфликты имён, `@use` против `@import`
   и дубли брейкпоинтов.
8. Поправить путь к entry в `.vscode/settings.json` →
   `liveSassCompile.settings.includeItems` под слаг темы.

### 1.2. Скачать сайт и зафиксировать baseline

1. Skill `project-ops` → `sync-down` (своя тема и свои плагины, не ядро WP).
2. **До любой правки:**

```bash
git init
git add .
git commit -m "baseline: состояние сервера на YYYY-MM-DD"
git tag baseline
```

Это точка отката. Без неё откатываться не к чему.

3. Приватный remote (GitHub/GitLab/Bitbucket) — иначе единственная копия лежит на диске:

```bash
git remote add origin <url>
git push -u origin main --tags
```

4. Дамп БД на сервере — git его не покрывает, а откат кода не вернёт контент,
   настройки ACF и опции:

```bash
wp db export backup-baseline.sql
```

### 1.3. Построить карту проекта

Команда агенту: **«построй структуру проекта»** (skill `project-structure`).
Заполнить шапку `project-base/INDEX.md`: назначение сайта, стек, префикс, text-domain,
правила проекта (только отклонения от глобальных), команды запуска и обязательные
проверки — критерий, при котором задача считается выполненной.

Карта каждой своей темы — `project-base/themes/<slug>/INDEX.md`, каждого своего
плагина — `project-base/plugins/<slug>/INDEX.md`. Пакетов может быть несколько.
Файлы и инструкции внутри пакета делятся на **фронт** и **бэк**, если слой есть
(шаблоны/SCSS/JS витрины vs PHP/админка/хуки). Пустой слой не заводить.

Дальше агент ходит по маршруту корневой INDEX → INDEX пакета → слой → детальный md →
точечный Read исходника (Grep / Glob при поиске), вместо сканирования репозитория
и без парсеров.

### 1.4. Сайт под ключ: этапы

Для greenfield-сайта (FSE). Каждый этап закрывается подтверждением пользователя: следующий строится на утверждённом.
В скобках — стек скиллов (`project-init` → `stack.md`, пакеты — `.claude/packages.json`).

| № | Этап | Что на выходе | Стек |
|---|------|---------------|------|
| 1 | Бриф | `.claude/product-marketing.md`: продукт, аудитория, тон, язык, конкуренты | `content` |
| 2 | Структура | Список страниц, URL, меню, перелинковка — `project-base/content/structure.md` | `content` (`site-architecture`) |
| 3 | Дизайн-система | Переменные и компоненты в Figma, имена = слаги `theme.json` | `figma` (`figma-generate-library`) |
| 4 | Макеты | Страницы в Figma: 375 / 768 / 1440 | `figma` (`figma-generate-design`) |
| 3–4′ | Дизайн без Figma | Макет в Claude Design (ссылка в `ACCESS.md`) или утверждённый план по `frontend-design` | `design` |
| 5 | Тексты и картинки | `project-base/content/<страница>.md`, картинки с `alt` | `content`, `seo` (`/seo image-gen`) |
| 6 | Тема | `theme.json` из переменных, шаблоны, части, паттерны, блоки; анимации — после вёрстки | `fse`, `blocks`, `interactivity`, `motion` |
| 7 | Магазин | Шаблоны Woo в блочной теме, корзина и оформление на блоках | `woo` |
| 8 | Сдача | Чек-лист 2.6 пройден, отчёт пользователю | `seo`, `quality` |

Тексты не ждут дизайна: этапы 2 и 5 можно вести параллельно с 3–4, но вёрстка идёт по утверждённым текстам, а не по lorem ipsum.

## 2. Цикл одной задачи

### 2.1. Запуск сессии — до первой задачи

Сайт живёт своей жизнью: клиент правит контент, плагины автообновляются,
другой подрядчик может залить файл. Если этого не проверить, git будет врать
о реальном состоянии сайта. Порядок строгий; простой вопрос без правок кода и сервера — сверку можно не запускать.

```bash
node .claude/skills/project-ops/scripts/session-check.mjs
```

Скрипт только читает (на сервере ничего не меняет) и печатает отчёт по шагам 0–2:

- **🖐 Сделать вручную** — открытые пункты из `INDEX.md` → «Сделать вручную»: напомнить пользователю одной строкой; «сделал» — проверить, если можно, и отметить `[x]`.

0. **Локально** — незакоммиченное и незапушенное с прошлого раза: закоммитить / запушить **до** сверки, чтобы свои правки не смешались с чужими.
1. **Сервер** (прод и stage, если есть `sftp-stage.json`):
   - свой код — `compare`: совпадают / изменены на сервере (чужие) / изменены локально (не залиты) / конфликт;
   - версии WordPress, плагинов, тем, mu-plugins против прошлой сессии (через SFTP, WP-CLI не нужен); обновился WooCommerce — список переопределений в теме для сверки `@version`;
   - быстрая проверка безопасности: ключевые файлы ядра против оригинала wordpress.org, лишний PHP в корне, PHP в `uploads` (известные кеши плагинов — не тревога), новые mu-plugins.
     🟡 — назвать пользователю, полная проверка — `project-init` → `recon.md`.
2. **Обновления** — скиллы (`skills-sync check`; хук `SessionStart` сообщает о них сам, раз в сутки). Есть — одной строкой предложить;
   после «да» — `skills-sync.mjs update <имена> --apply` и отдельный коммит. Проверка версии шаблона — после части E плана.

Дальше по отчёту:

- **чужие правки** — `sftp-sync.mjs sync-down` (скачает только их) и отдельный коммит:

  ```bash
  git add -A
  git commit -m "sync: изменения с сервера (не мои)"
  ```

- **не залито** — предложить залить (`upload` или `deploy` — по режиму заливки);
- **конфликт** — показать разницу и решить с пользователем; `sync-down --force` — только после его решения;
- **нет связи с сервером** — работать можно, но заливки только после успешной сверки.

3. **Задача** — профиль проекта и только нужное по задаче.

Отчёт пользователю — 3–4 строки, например:

> Локально: чисто. Сервер: 2 файла изменены не вами (скачаны, коммит `sync`), конфликтов нет. Безопасность: 🟢. WooCommerce 8.9 → 9.3 — сверю шаблоны в теме. Скиллы: актуальны.

### 2.2. Работа

- Одна задача = одна ветка (`feat/hero-block`) либо, если работаете в `main`, — серия
  осмысленных коммитов. Ветка предпочтительнее: её легко выбросить целиком.
- Перед рискованной правкой (переписывание шаблона, апдейт Woo, миграция блока) — тег:

```bash
git tag before-woo-update
```

- Для задачи длиннее одного захода — короткая заметка `project-base/tasks/<slug>.md`:
  что делаем, какие файлы затронуты, какие решения приняты. Агент читает её вместо
  восстановления контекста из переписки. После завершения задачи файл удаляется.
- Архитектурные решения, которые переживут задачу («почему блок, а не паттерн»),
  — запись в `project-base/DECISIONS.md`: решение, причина, следствие, статус. Редко,
  только то, о чём через полгода спросят «почему так». Агент обязан следовать
  записанному и не предлагать заново отброшенные варианты.

### 2.3. Коммиты

Гранулярность: один логичный шаг — один коммит. «Правки» и «фиксы» в сообщениях
бесполезны при откате.

Формат: `<область>: <что сделано>`

```
theme: хедер на sticky при скролле
blocks: динамический блок отзывов, render.php
woo: убран sidebar на странице товара
sync: изменения с сервера (не мои)
build: пересборка после правок src/
```

Область — `theme`, `blocks`, `woo`, `plugin`, `scss`, `sync`, `build`, `docs`.

### 2.4. Заливка на сервер

Человек сохранил в редакторе — `uploadOnSave` уже залил (это ручная работа в Cursor).

Правки агента — по режиму из `ACCESS.md` (решение 012):

- `guarded-auto` (по умолчанию): хук `.claude/hooks/post-edit.mjs` после каждой правки в своей теме/плагине
  делает `php -l` (локально, иначе на сервере), сохраняет серверную версию файла, заливает, проверяет главную
  (HTTP < 500) и новые `PHP Fatal|Parse` в `debug.log`. При ошибке файл на сервере откатывается,
  локальная правка остаётся — агент чинит и правит снова.
- `stage-auto`: то же, но на stage (`.vscode/sftp-stage.json`, Stage URL).
- `manual`: агент заливает только по команде («залей», «выложи», «задеплой») или после «да».

Хук проверяет главную и лог, а не каждую страницу: fatal в шаблоне одной страницы он не увидит —
это проверка агента в браузере. Хук видит только Write / Edit / MultiEdit: SCSS-компилятор и `npm run build`
работают через Bash, поэтому CSS и `build/` агент заливает сам после сборки (`sftp-sync.mjs upload`,
при `stage-auto` с `--stage`). `build/` коммитить вместе с `src/`. Нет SSH/SFTP — заливка не работает, режим фактически `manual`.

Коммит — после проверки в браузере.

### 2.5. Завершение задачи

- Обновить карту: изменился набор функций в файле → его детальный md в
  `themes/<slug>/front|back/` или `plugins/<slug>/front|back/`; новый важный файл →
  строка в INDEX этого пакета в нужном слое.
- Удалить `project-base/tasks/<slug>.md`.
- `git push`.

### 2.6. Сдача сайта

Перед передачей клиенту и после крупного редизайна (этап 8 из 1.4). Агент проходит список сам и отдаёт отчёт:
пункт — статус — что сделать. Непройденный пункт без решения пользователя = сайт не сдан.
Стеки `seo` и `quality`; команды `/seo …` — из плагина `claude-seo`.

**Контент и разметка**
- [ ] Одна `h1` на страницу, заголовки без пропусков уровней; title и description уникальны (`/seo page`).
- [ ] Качество и E-E-A-T, фактов без источника нет (`/seo content`, правило `content`); плейсхолдеров `[уточнить: …]` и lorem ipsum не осталось.
- [ ] Schema.org: Organization или LocalBusiness, WebSite, BreadcrumbList; магазин — Product/Offer с ценой и наличием. Без ошибок валидации (`/seo schema`).

**Индексация**
- [ ] Прод открыт для поиска (`wp option get blog_public` = 1), stage закрыт.
- [ ] `robots.txt` не закрывает нужное, `sitemap.xml` отдаётся и указан в robots (`/seo sitemap`).
- [ ] `canonical` на всех шаблонах; один вариант адреса (www, https, слеш) — остальные 301.
- [ ] Search Console: свойство подтверждено, sitemap отправлен, ошибок покрытия нет (`/seo google`, `ACCESS.md` → «SEO и аналитика»).

**AI-видимость**
- [ ] AI-краулеры (GPTBot, ClaudeBot, PerplexityBot, Google-Extended) не закрыты без решения клиента; решение — в `DECISIONS.md` (`/seo geo`).
- [ ] `llms.txt` — по решению клиента; ключевые страницы читаются без JS.

**Скорость** (скилл `core-web-vitals`, `/seo technical`)
- [ ] Мобильные LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1: главная, категория, товар, статья.
- [ ] Картинки WebP/AVIF с `width`/`height`, `loading="lazy"` ниже первого экрана, у hero `fetchpriority="high"`; шрифты локально, `font-display: swap`.
- [ ] Стили и скрипты блоков — только там, где блоки есть; кеш страниц включён.

**Доступность** (скилл `accessibility`)
- [ ] Контраст AA, видимый фокус, всё работает с клавиатуры, skip-link, `lang` у `html`, у полей форм есть `label`.
- [ ] Магазин: корзину и оформление можно пройти клавиатурой, ошибки форм объявляются.

**Магазин** (стек `woo`)
- [ ] Тестовый заказ на stage проходит до письма клиенту; письма в стиле сайта; свой код совместим с HPOS.
- [ ] Страницы политики, условий, доставки и возврата есть и стоят в подвале.

**Техника**
- [ ] `debug.log` без ошибок от своего кода; `WP_DEBUG_DISPLAY` на проде выключен.
- [ ] Страница 404 оформлена, формы отправляются, старые URL (при редизайне) — 301.
- [ ] `/seo drift baseline <url>` — точка отсчёта для будущих регрессий.

**Европа (GDPR)** — если посетители в Европе (`INDEX.md` → «Профиль проекта»)
- [ ] Баннер согласия на cookies; аналитика и пиксели — только после согласия.
- [ ] Шрифты и скрипты — с сервера сайта, не с CDN Google (`recon.mjs` → домены в окружении).
- [ ] Политика конфиденциальности; Германия, Австрия, Швейцария — Impressum.

**Передача**
- [ ] Обязательные проверки из `INDEX.md` и `handoff` каждого выбранного пакета (`.claude/packages.json`) — пройдены.
- [ ] Пользователь агента на проде удалён (`wp user delete claude-agent --reassign=<ID>` после «да» или админка — `no-wpcli.md`); на stage — по решению.
- [ ] Новый сайт запущен → режим заливки пересмотрен: обычно `stage-auto` или `manual` (`ACCESS.md` → «Заливка»).
- [ ] Stage: закрыт от индексации и паролем или удалён (`project-ops` → `stage.md`).
- [ ] Выкатка последняя, тег `deploy-*` запушен (`git push --tags`); незалитого и незакоммиченного нет (`session-check`).
- [ ] «Сделать вручную» в `INDEX.md` — закрыто или передано клиенту списком.
- [ ] Пакет «Обучение клиента» — инструкция передана, клиент вошёл под своей учётной записью.

Отчёт — `project-base/launch-<дата>.md` и коротко в чат.

## 3. Откат

### Откатить один файл к рабочему состоянию

```bash
git log --oneline -- wp-content/themes/{stem}-theme/functions.php
git checkout <hash> -- wp-content/themes/{stem}-theme/functions.php
```

Затем **залить файл** (`project-ops` → `upload`) — git меняет только локальную
копию, на сервере останется сломанная версия, пока не сделан upload.

### Откатить всю задачу

```bash
git revert <hash>          # безопасно, история сохраняется
```

Далее — upload затронутых файлов на сервер.

### Вернуться к состоянию до рискованной правки

```bash
git checkout before-woo-update -- .
```

Проверить `git status`, залить изменённое на сервер.

### Что git не откатит

БД: контент, настройки плагинов, поля ACF, опции темы, заказы Woo.
Для этого нужен дамп, снятый **до** задачи (`wp db export`). Правило простое:
задача трогает настройки или контент — сначала дамп.

## 4. Разрешения агента

Всё в `.claude/settings.json`, коммитится. Логика: агент работает самостоятельно, границы держат хуки и `deny`.

**Режим:** `defaultMode: acceptEdits` — правки файлов без запроса; куда можно писать, решает `guard-paths` (свои пакеты из `project.json`).

**Без запроса (`allow`):** `compile-scss`, `gen-whitelist`, `skills-sync` (кроме `--apply`, он с подтверждением), `sftp-sync test|download|upload|sync-down`, `ssh-exec test`, WP-CLI на чтение
(`plugin list`, `theme list`, `option get`, `core version`, `user list`, `post list`, `cache flush`, `rewrite flush`, `db export`, `db check`; с `--stage` и без),
`git status|diff|log|show|add|commit`, `npm run build|start`, `php -l|-v`, `node -v`, `npm -v`, Playwright MCP, документация на `developer.wordpress.org`, `wordpress.org`,
`make.wordpress.org`, `developer.woocommerce.com`, `woocommerce.com`, `advancedcustomfields.com`, `developer.mozilla.org`.

**С подтверждением (`ask`):** `git push`, правка `.mcp.json`, `.vscode/sftp*.json`, `ssh*.json`; `put`, `remove`, `sync-up`; `ssh-exec -- <cmd>`, которых нет в разрешённых.

**Запрещено (`deny`):** чтение секретов, дампов, `*.sql`, `*.map`, `*.min.*`; правка `wp-config.php`, `wp-admin/`, `wp-includes/`, `.git/`, **`.claude/hooks/`, `.claude/settings*.json`**;
`rm -r`, `Remove-Item -Recurse`, `git reset --hard`, `git clean`, `git push --force`, `npm publish`, `curl`, `wget`, `Invoke-WebRequest`, `Invoke-Expression`, `sudo`, прямые `ssh`/`scp`/`sftp`/`rsync`.

### Хуки (`.claude/hooks/`)

| Хук | Событие | Что делает |
|-----|---------|------------|
| `guard-paths` | Write / Edit | Правки только в своих пакетах; ядро WP, хуки, настройки агента, `.git` закрыты |
| `guard-bash` | Bash / PowerShell | Та же граница для записи через оболочку (`>`, `tee`, `sed -i`, `cp`, `mv`, `rm`, `Set-Content`, `Remove-Item`…) |
| `guard-wpcli` | Bash / PowerShell | Команды после `ssh-exec.mjs --`: запись на сервере и секреты — deny; изменяющий WP-CLI — ask и автодамп БД; чтение — allow |
| `post-edit` | после Write / Edit | `phpcs`/`stylelint` (отчёт агенту), `php -l`, бэкап, заливка, проверка сайта, откат; счётчик попыток (лимит 3); журнал |
| `stop-map` | Stop | Один раз напомнит обновить карту после структурных правок |
| `skills-sync.mjs check --hook` | SessionStart | Раз в сутки сверяет скиллы с апстримом; есть обновления подключённых — одна строка агенту (решение 022) |

`node .claude/hooks/selftest.mjs` — самопроверка охранников без сервера. Журнал — `.claude/.state/audit.log` (в git не идёт).
Ограничения: хуки не видят запись из скриптов (`node script.mjs`, `npm run build`); `guard-wpcli` разбирает только вызовы `node …ssh-exec.mjs`.
Хуки и настройки правит только человек, вручную в редакторе: `permissions.deny` на Edit этих файлов действует всегда. `CLAUDE_TEMPLATE_DEV=1` (переменная окружения при запуске `claude`) отключает лишь проверки хуков `guard-paths` и `guard-bash`, `deny` не снимает.

Пароль в `sftp.json` / `ssh.json` не цитировать в чат. Факты доступов — `ACCESS.md`: записал — не спрашивать снова.
Личные разрешения (`.claude/settings.local.json`) в git не идут.

### Границы механизма

- `permissions.deny` и хуки защищают инструменты Claude. Команда внутри скрипта или MCP-сервер может прочитать файл в обход. Секреты в репозитории от этого не защищены:
  пароли в `sftp.json` / `ssh.json` там лежат осознанно (решение 002), репозиторий должен быть приватным.
- Playwright `--allowed-origins` не граница безопасности (не влияет на редиректы): запрет сторонних сайтов держит правило `safety`.

## 5. Что где лежит

| Что | Где | Зачем |
|-----|-----|-------|
| Операции (SFTP, SSH, SCSS, сборка) | skill `project-ops` | Один метод на задачу, скрипты в скилле |
| Доступы (SFTP, SSH, WP-CLI, URL, админка, браузер, Figma) | `ACCESS.md` + `.vscode/ssh.json` / `sftp.json` | Память агента: не переспрашивать; сбор при старте — `project-init` → `access.md` |
| Правила «как писать код» | `CLAUDE.md` + `.claude/rules/*.md` (стек — из `.claude/rules-optional/`) | Одинаковы для всех проектов |
| Описание проекта, карта кода | `project-base/INDEX.md` + `themes/<slug>/{front,back}/`, `plugins/<slug>/{front,back}/` | Пакет → слой → файл, без скана репозитория |
| Чтение исходников | Read / Grep / Glob (правило `read-code`) | Не парсеры, не `detect_*.mjs`, не обход через Shell |
| SCSS-заготовка | `project-base/_starter/` | Копируется в тему/плагин при старте |
| Скрины редизайна | `project-base/screenshots/` | Референс старого сайта, в git |
| Дампы БД | на сервере (`../claude-backup-<время>.sql`, бэкап хостинга) | Не в git (персональные данные); агент не читает |
| SFTP/FTP-конфиг | `.vscode/sftp.json`, `.vscode/sftp-ftp.json` | В git |
| Слаги и префикс | `project-base/project.json` | Источник для whitelist в `.gitignore` и `sftp.json` |
| Хуки и разрешения агента | `.claude/settings.json`, `.claude/hooks/` | Границы правок, заливка, напоминание о карте; защищены от правки агентом |
| Проверки стиля | `.stylelintrc.json`, `phpcs.xml.dist` | stylelint (SCSS, BEM) и phpcs (WordPress) из post-edit |
| Правила безопасности и вёрстки | `.claude/rules/safety.md`, `layout-check.md` | Недоверенный контент, админка, лимит попыток; проверка ширин и семантики |
| Скиллы: источники, версии, стеки | `.claude/skills.json` + `skills-sync.mjs` (`project-ops` → `skills.md`) | Подключение по стеку, проверка и обновление из апстрима |
| Бриф для контента | `.claude/product-marketing.md` | Читают скиллы стека `content` |
| Тексты страниц, структура, промпты картинок | `project-base/content/` | Клиент читает и правит до переноса в WP |
| Отчёт о сдаче | `project-base/launch-<дата>.md` | Чек-лист 2.6 |
| Хронология изменений | git log | История и откат |
| Контекст активной задачи | `project-base/tasks/<slug>.md` | Живёт до конца задачи |
| Архитектурные решения, «почему так» | `project-base/DECISIONS.md` | Редко, надолго; агент им следует |
| Почему так устроен шаблон | `.claude/template/DECISIONS.md` | Обновляется вместе с шаблоном |

Хронологию работ **не** вести в markdown: агент будет её перечитывать и тратить
контекст на то, что уже есть в `git log`.

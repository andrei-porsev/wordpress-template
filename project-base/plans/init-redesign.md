# План: поэтапная инициализация проекта

Рабочий план переделки `project-init`. Согласованы все этапы 1–10; реализация — частями A–F (раздел «Порядок реализации»).
После согласования всех этапов план переносится в скиллы, правила и скрипты, а этот файл удаляется.
Текущий `project-init/types.md` (4 типа) — промежуточная версия, будет переписан по этому плану.

## Принципы опроса

- Каждый вопрос — со строкой «Зачем:», термины пояснены с примером, у вариантов — описание.
- **Сводка перед записью:** ответы копятся, в конце один экран «что получилось» → запись после «да».
- **Прогресс сохраняется:** прерванная инициализация продолжается с того же этапа.
- **Технические поля предлагает агент:** слаг, префикс, text-domain, путь к SCSS — из названия или кода; пользователь подтверждает.
- **Проверка машины отдельно от проекта:** Node, PHP, phpcs, MCP, SSH-ключ — один раз на компьютер, в проектах не повторять.
- «Процессы» и «Ограничения» на старте не спрашивать: команды — из стека, ограничения — один вопрос для клиентского сайта, остальное при первой задаче.
- Пробная заливка — только когда на сервере живой сайт.
- Пользователь — веб-разработчик, не SEO-специалист: в маркетинговых вопросах агент ведёт сам (наводящие вопросы, черновики ответов).
- **Агент работает только внутри проекта.** Всё вне проекта (SSH-ключи, личная папка `~/.wp-template/`) — только через скрипты шаблона;
  агент эти файлы своими инструментами не читает и не правит, видит краткий вывод скрипта.

### 1. Тип проекта

Два уровня вопроса:

- **Новый** → `нужен дизайн` / `дизайн есть`.
- **Существующий** → `доработка` / `редизайн` (тоже `нужен дизайн` / `дизайн есть`) / `переезд` / `SEO и скорость`.
- Для существующего — «Вы уже работали с этим сайтом?» → `нет, после другого разработчика` добавляет аудит (`project-base/audit.md`, временно стек `triage`) перед маршрутом.

Отдельного типа «взлом и лечение» нет — вместо него проверка безопасности на этапе 4.

Маршруты: «новый» — как в текущем `types.md` (FSE, своя тема; «нужен дизайн» — все этапы `WORKFLOW.md` → 1.4, «дизайн есть» — без макетов).
«Переезд»: копию сайта и БД переносит человек (Duplicator, All-in-One WP Migration, WP Toolkit, хостинг); агент — доступы к обоим серверам, снимок до, `search-replace` (`--dry-run`, потом «да»), чек-лист после (HTTPS, редиректы, permalinks, формы, почта, cron, кеш), сравнение до/после; стеки `wpcli`, `seo`.
«SEO и скорость»: доступы, копия, сразу «SEO и аналитика», замеры «до»; стеки `seo`, `quality`, `perf`; дизайн и анимации пропускаются.

### 2. О проекте и бриф

- Вопросы: название, домен (есть / ещё нет), **вид сайта** (лендинг / корпоративный / магазин / блог или медиа / каталог или сервис / портфолио), **главные действия посетителя** (→ «Обязательные проверки» в INDEX), **языки**, **где посетители** (США / Европа / весь мир → проверки GDPR: cookies, локальные шрифты и скрипты, политика).
- Stage — в этап 8; объём работ — в этап 6.
- Существующий сайт — предзаполнение: `blogname`, `siteurl`, языки по плагину перевода, вид по плагинам и главной; назначение — агент читает главную и предлагает формулировку. Спросить только главные действия посетителя.
- **Бриф с агентом:** на каждый вопрос агент сразу даёт черновик ответа по нише.
  - Короткий — всегда: оффер, кто покупает, география (город → локальное SEO, `seo-local`, `LocalBusiness`).
  - Полный — при пакетах контента, SEO или дизайна: + почему выбирают, конкуренты (агент найдёт 3 сайта), поисковые запросы (`seo-plan`, `seo-cluster`; без DataForSEO — без частотности), тон («ты/вы», пробные фразы), что нельзя обещать; для дизайна — стиль, логотип, цвета, шрифты, фото, референсы «нравится / не нравится».
  - Результат: `.claude/product-marketing.md` и черновик структуры (страницы, адреса, запросы).
  - Проверить скилл `product-marketing-context` в `coreyhaines31/marketingskills` — подключить в стек `content` вместо своих вопросов.

### 3. Доступы и окружения

- **Хостинг** (подсказывает настройки) → **данные для входа** (можно вставить письмо хостинга; пароль сразу в json, в чате не повторять) → агент сам проверяет SSH, путь к WP (по `wp-config.php`), WP-CLI → подтверждение итога.
- **Цепочка подключения:** SSH + SFTP → только SFTP → FTPS → FTP (с предупреждением об открытом пароле).
- **Без SSH:** локальный PHP обязателен (PHP из OSPanel / LocalWP); `debug.log` — через SFTP/FTP; WP-CLI-шаги — ручные инструкции (Better Search Replace, бэкап в панели, пользователь в админке), агент проверяет результат.
- **Помощник SSH:** ключ `ed25519` (создать после «да», `.ppk` → OpenSSH); инструкции под панель — Plesk на IONOS (подписка со своим пользователем, `/bin/bash`, ключ в `authorized_keys`, фаерволы Plesk и IONOS), популярные хостинги США и Европы (управляемые WP — встроенный stage; shared — SSH выключен или нестандартный порт); письмо клиенту (EN / RU) «включите SSH и добавьте ключ»; таблица диагностики (таймаут, refused, auth failed, выкинуло, `wp` не найден, сменился ключ сервера → стоп); **не больше 2 попыток входа** (Fail2Ban).
- **Окружения** (несколько вариантов): прод / stage (`у клиента` / `мой VPS` / нет) / локально (LocalWP, OSPanel).
- Свой VPS (IONOS + Plesk) — только stage и промежуточные копии; доступ администратора Plesk агенту не даётся, агент работает под пользователем подписки.
- Админка и тестовый пользователь — этап 7 (пользователя создаёт человек или агент командой WP-CLI после «да»).

### 4. Разведка, проверка безопасности, копия, анализ

Порядок: разведка → проверка безопасности → скачивание и baseline → анализ.

- **Разведка:** список тем и плагинов (WP-CLI или папки по SFTP); агент сам определяет активную тему, родителя и **свой код** (без источника обновлений, нестандартное имя) → подтверждение → `project.json` → whitelist.
- **Проверка безопасности до скачивания** (только чтение): `verify-checksums` ядра и плагинов, PHP в `uploads`, вредоносные шаблоны, лишние администраторы, `siteurl`/`home`, `mu-plugins`, drop-in, `.htaccess`, даты изменений (у `wp-config.php` — только дата), Google Safe Browsing / Sucuri SiteCheck. Без SSH — по списку файлов, с пометкой «содержимое не проверено».
  - 🟢 чисто — одна строка, дальше;
  - 🟡 подозрительно — список с пояснениями, ждать решения;
  - 🔴 признаки заражения — стоп, находки, рекомендация (лечение, пароли, что сказать клиенту), ждать решения.
  - «Приостановить» — прогресс с отметкой, при возобновлении проверка повторяется. «Продолжить на риск» — подозрительные файлы не скачивать и не в git, режим заливки `manual`, решение в `DECISIONS.md` и `audit.log`.
  - Отчёт `project-base/security-check.md` — всегда («как было до нас»).
  - Быстрая версия (checksums + PHP в `uploads`) — перед каждой задачей при сверке с сервером.
- **Baseline:** коммит и тег `baseline`; дамп БД остаётся на сервере (персональные данные, GDPR), без SSH — бэкап делает человек.
- **Анализ:** режим, тема, сборка, SCSS, префикс; устаревшие плагины и PHP; свежие ошибки `debug.log`; окружение; данные для этапа 2. Чужие правки и старые ошибки — в отчёт с датой.
- Глубина: доработка / SEO / переезд — короткий; после другого разработчика — полный аудит; редизайн с новой темой — старую тему только читаем. Карта (`project-structure`) — сразу для доработки и аудита.
- Родительская тема и сторонние плагины — скачивание для чтения по запросу, вне git.

### 5. Стек и свой код

Вместо технических вопросов (FSE / classic / билдер, слаги) — вопросы о работе клиента и сайта; технику агент выводит сам.

**Новый сайт:**

1. **«Как клиент будет править сайт после сдачи?»**

   | Ответ | Стек |
   |---|---|
   | меняет тексты и картинки в готовых секциях | FSE + блоки с полями (ACF) и заблокированные паттерны |
   | сам собирает страницы из готовых секций | FSE + библиотека паттернов |
   | визуальный конструктор, двигает всё сам | билдер (Elementor / Bricks) + стили в дочерней теме; агент один раз называет цену: скорость, поддержка, риск сломать вёрстку |
   | сам не правит, всё через нас | FSE |

2. **«Есть ли лицензия ACF Pro?»** — `да` → секции с полями на ACF; `нет` → нативные блоки со сборкой. Интерактив (фильтры, табы, калькуляторы) — нативные блоки всегда.
3. **«Есть ли функции, которые должны пережить смену темы?»** (свои типы записей, CRM, расчёты) — `да` → плагин `{stem}-core`; `нет` → всё в теме.
   mu-plugins и слаги блоков на старте не спрашивать: mu-plugin — когда понадобится, блок — в `project.json` при создании.
4. **Базовый набор плагинов** — агент предлагает по виду сайта и географии; любимых плагинов у пользователя нет, набор составляет агент.
   Пример (корпоративный, Европа): SEO — Yoast / Rank Math; формы — по задаче; кеш — по хостингу; безопасность — Wordfence; бэкапы — UpdraftPlus или хостинг; cookies и GDPR — Complianz / CookieYes.
   Пользователь правит список; установка — WP-CLI после «да». Наборы по видам сайтов — основа будущих пакетов услуг.
5. Префикс, слаг, text-domain, версии PHP и WP — без вопросов (из названия, с сервера или последние стабильные), в сводку этапа 9.

**Существующий сайт** (доработка, SEO, переезд) — сводка найденного на этапе 4 и только:

1. Дочерней темы нет → `создать (рекомендую)` / `правим тему напрямую`.
2. Сайт на билдере → «Новые секции в билдере (клиент правит сам) или кодом в теме (быстрее, правит разработчик)?»
3. Куда новый функционал — агент рекомендует по правилу шаблона (дочерняя тема; плагин — для переносимого), пользователь подтверждает.

**Редизайн:** рестайл — как существующий сайт; новая тема — вопрос 1 нового сайта; режим отличается от текущего → запись в `DECISIONS.md` проекта.

**Уходит из опроса:** сборка и SCSS — из стека (нативные блоки → `@wordpress/scripts`, SCSS → Live Sass в Cursor или `compile-scss`);
лицензии платных плагинов и тем, заброшенные и лишние плагины — в аудит этапа 4.

### 6. Объём работ → пакеты услуг

что сдаётся клиенту, проверки при сдаче (`WORKFLOW.md` → 2.6), описание для клиента RU / EN (2–3 строки для коммерческого предложения).

**Не спрашивается — уже известно:** дизайн (тип проекта), магазин (вид сайта → `woo`), многоязычность (языки → плагин перевода, `seo-hreflang`), локальный бизнес (география = город → `seo-local`).

|---|---|---|---|

| Редактура текстов | правка и вычитка текстов клиента | `content` (`copy-editing`) | где тексты клиента |

| Скорость и доступность | Core Web Vitals, доступность, отчёт до и после | `quality` | — |
| Анимации | сценарии при прокрутке, анимация текста | `motion` | какие страницы и что анимировать |
| Сопровождение | ежемесячно: обновления сначала на stage, проверка безопасности, бэкапы, отчёт клиенту | `wpcli`, `quality` | периодичность, кому отчёт |
| Перенос контента | страницы, записи, медиа со старого сайта; карта редиректов старых адресов (Redirection или `.htaccess`) | `wpcli`, `seo` | откуда (WordPress / другая CMS / статичный сайт), объём, сохраняются ли адреса |
| Интеграции | CRM, оплаты (Stripe, PayPal), рассылки, аналитика | `plugin`, `rest` | какие сервисы, есть ли у клиента аккаунты и тестовые ключи; агент работает только в тестовом режиме, боевые ключи вводит человек |

- Выбранные пакеты — в профиль проекта; подключаются только их правила и скиллы (раздел «Контекст»).
- По типам: новый — все доступны; доработка — ничего не отмечено; редизайн — «Базовое SEO» и «Скорость и доступность» отмечены (сравнить до и после);
  SEO и скорость — оба включены; переезд — «Базовое SEO» (адреса и редиректы) включено.

### 7. Сайт, браузер, админка, макет

**Агент выясняет сам:** адреса прода, stage и локальный (этапы 2–3); адрес входа в админку (`/wp-admin`, перенесённый плагином — по его настройкам);
доступ к БД (из этапа 3); источник макета (этап 1 — здесь только ссылка и подключение); ширины — из макета или стартера;
разрешённые домены браузера — прод, stage, локальный + CDN с первой загрузки, пользователь подтверждает. «Проверять ли в браузере» не спрашивать — проверка обязательна; вопрос только если браузер не подключился.

**Спрашивается:**

1. **Пользователь агента** (`claude-agent`):

   | Окружение | Роль |
   |---|---|
   | локально, stage | администратор постоянно |
   | прод | редактор; администратор — по задаче: `wp user set-role` после «да», после задачи обратно; оба действия в `audit.log` |

   - Админка в браузере — только просмотр: ничего не сохранять, не удалять, не публиковать, не обновлять. Изменения — только через WP-CLI (охранник, подтверждение, дамп); возможны только в админке — агент описывает шаги, нажимает человек.
   - Пароль длинный, уникальный на проект, в `ACCESS.md`, в чате не показывать; браузер `--isolated`, вход каждый раз.
   - Двухфакторный вход: агент коды не вводит — на проде остаётся редактором или пользователь исключает его из 2FA только на stage.
   - Прод: рекомендовать журнал действий (Simple History).
   - Создание: локально и на stage — WP-CLI после «да»; на проде — после «да» с предупреждением. **При сдаче — удалить на проде** (пункт в `WORKFLOW.md` → 2.6).
2. **Пароль на stage** (защита каталога) — логин и пароль в `ACCESS.md` → stage; передать браузеру без пароля в адресе (способ проверить).
3. **Figma** — подключение `/mcp` → `figma` → Authenticate, агент проверяет.

**Скриншоты «до»** (существующие сайты): главная и страницы главных действий посетителя → `project-base/screenshots/before/`, в git — сжатые снимки ключевых страниц.
Ширины: каждый брейкпоинт темы с обеих сторон (768 → 767 и 768) + 375, 1440, 1920; значения ближе 20 px объединять; во всю высоту; на каждой ширине — проверка горизонтальной прокрутки.

**Брейкпоинты темы** — агент ищет: переменные и миксины SCSS, `@media` в собранном CSS темы и плагинов вёрстки, `contentSize` / `wideSize` в `theme.json`, настройки билдера (WP-CLI, чтение), фреймворк темы (Bootstrap, Tailwind).
Результат — в профиль проекта; `layout-check` проверяет по ним каждую правку вёрстки. Новая тема — стартер и макет; расхождение — сказать.

Вопросов: новый без Figma — 1; с Figma — 1 + подключение; существующий — 1–2 + подтверждение сводки адресов (было 7–15).

### 8. Режим заливки

Режим по умолчанию выбирает агент:

| Ситуация | Режим |
|---|---|
| новый, сервера нет | `local` (есть локальный сайт) или `manual` |
| новый, сайт не запущен | `guarded-auto` на прод |
| существующий, stage есть | `stage-auto` |
| существующий, stage нет | вопрос |
| редизайн, новая тема неактивной на проде | `guarded-auto` |
| работа на локальной копии | `local` |
| переезд, SEO и скорость | `stage-auto` или `manual` |

Единственный вопрос — существующий сайт без stage: `manual (рекомендую для магазинов и сайтов с трафиком)` / `guarded-auto` (небольшие сайты; проверка и откат) / `завести stage на моём VPS` → этап 3, `stage-auto`.

**Выкатка на прод** (со stage или локального сайта) — команда «выкати на прод»; способ переноса у пользователя бывает разным, он следует рекомендациям агента:

1. Сверка прода; чужие правки после последней выкатки → стоп.
2. Список файлов — изменения в git с тега `deploy-<дата>` (первый раз — с `baseline`), с пояснениями.
3. «Да» пользователя.

# План: поэтапная инициализация проекта

Рабочий план переделки `project-init`. Согласованы этапы 1–4; этапы 5–10 — в обсуждении.
После согласования всех этапов план переносится в скиллы, правила и скрипты, а этот файл удаляется.
Текущий `project-init/types.md` (4 типа) — промежуточная версия, будет переписан по этому плану.

## Принципы опроса

- Каждый вопрос — со строкой «Зачем:», термины пояснены с примером, у вариантов — описание.
- **Сводка перед записью:** ответы копятся, в конце один экран «что получилось» → запись после «да».
- **Прогресс сохраняется:** прерванная инициализация продолжается с того же этапа.
- **Технические поля предлагает агент:** слаг, префикс, text-domain, путь к SCSS — из названия или кода; пользователь подтверждает.
- **Проверка машины отдельно от проекта:** Node, PHP, phpcs, MCP, SSH-ключ — один раз на компьютер, в проектах не повторять.
- «Процессы» и «Ограничения» на старте не спрашивать: команды — из стека, ограничения — один вопрос для клиентского сайта, остальное при первой задаче.
- Пробная заливка — только когда на сервере живой сайт.
- Пользователь — веб-разработчик, не SEO-специалист: в маркетинговых вопросах агент ведёт сам (наводящие вопросы, черновики ответов).

### 1. Тип проекта

Два уровня вопроса:

- **Новый** → `нужен дизайн` / `дизайн есть`.
- **Существующий** → `доработка` / `редизайн` (тоже `нужен дизайн` / `дизайн есть`) / `переезд` / `SEO и скорость`.
- Для существующего — «Вы уже работали с этим сайтом?» → `нет, после другого разработчика` добавляет аудит (`project-base/audit.md`, временно стек `triage`) перед маршрутом.

Отдельного типа «взлом и лечение» нет — вместо него проверка безопасности на этапе 4.

Маршруты: «новый» — как в текущем `types.md` (FSE, своя тема; «нужен дизайн» — все этапы `WORKFLOW.md` → 1.4, «дизайн есть» — без макетов).
«Переезд»: копию сайта и БД переносит человек (Duplicator, All-in-One WP Migration, WP Toolkit, хостинг); агент — доступы к обоим серверам, снимок до, `search-replace` (`--dry-run`, потом «да»), чек-лист после (HTTPS, редиректы, permalinks, формы, почта, cron, кеш), сравнение до/после; стеки `wpcli`, `seo`.
«SEO и скорость»: доступы, копия, сразу «SEO и аналитика», замеры «до»; стеки `seo`, `quality`, `perf`; дизайн и анимации пропускаются.

### 2. О проекте и бриф

- Вопросы: название, домен (есть / ещё нет), **вид сайта** (лендинг / корпоративный / магазин / блог или медиа / каталог или сервис / портфолио), **главные действия посетителя** (→ «Обязательные проверки» в INDEX), **языки**, **где посетители** (США / Европа / весь мир → проверки GDPR: cookies, локальные шрифты и скрипты, политика).
- Stage — в этап 8; объём работ — в этап 6.
- Существующий сайт — предзаполнение: `blogname`, `siteurl`, языки по плагину перевода, вид по плагинам и главной; назначение — агент читает главную и предлагает формулировку. Спросить только главные действия посетителя.
- **Бриф с агентом:** на каждый вопрос агент сразу даёт черновик ответа по нише.
  - Короткий — всегда: оффер, кто покупает, география (город → локальное SEO, `seo-local`, `LocalBusiness`).
  - Полный — при пакетах контента, SEO или дизайна: + почему выбирают, конкуренты (агент найдёт 3 сайта), поисковые запросы (`seo-plan`, `seo-cluster`; без DataForSEO — без частотности), тон («ты/вы», пробные фразы), что нельзя обещать; для дизайна — стиль, логотип, цвета, шрифты, фото, референсы «нравится / не нравится».
  - Результат: `.claude/product-marketing.md` и черновик структуры (страницы, адреса, запросы).
  - Проверить скилл `product-marketing-context` в `coreyhaines31/marketingskills` — подключить в стек `content` вместо своих вопросов.

### 3. Доступы и окружения

- **Хостинг** (подсказывает настройки) → **данные для входа** (можно вставить письмо хостинга; пароль сразу в json, в чате не повторять) → агент сам проверяет SSH, путь к WP (по `wp-config.php`), WP-CLI → подтверждение итога.
- **Цепочка подключения:** SSH + SFTP → только SFTP → FTPS → FTP (с предупреждением об открытом пароле).
- **Без SSH:** локальный PHP обязателен (PHP из OSPanel / LocalWP); `debug.log` — через SFTP/FTP; WP-CLI-шаги — ручные инструкции (Better Search Replace, бэкап в панели, пользователь в админке), агент проверяет результат.
- **Помощник SSH:** ключ `ed25519` (создать после «да», `.ppk` → OpenSSH); инструкции под панель — Plesk на IONOS (подписка со своим пользователем, `/bin/bash`, ключ в `authorized_keys`, фаерволы Plesk и IONOS), популярные хостинги США и Европы (управляемые WP — встроенный stage; shared — SSH выключен или нестандартный порт); письмо клиенту (EN / RU) «включите SSH и добавьте ключ»; таблица диагностики (таймаут, refused, auth failed, выкинуло, `wp` не найден, сменился ключ сервера → стоп); **не больше 2 попыток входа** (Fail2Ban).
- **Окружения** (несколько вариантов): прод / stage (`у клиента` / `мой VPS` / нет) / локально (LocalWP, OSPanel).
- Свой VPS (IONOS + Plesk) — только stage и промежуточные копии; доступ администратора Plesk агенту не даётся, агент работает под пользователем подписки.
- Админка и тестовый пользователь — этап 7 (пользователя создаёт человек или агент командой WP-CLI после «да»).

### 4. Разведка, проверка безопасности, копия, анализ

Порядок: разведка → проверка безопасности → скачивание и baseline → анализ.

- **Разведка:** список тем и плагинов (WP-CLI или папки по SFTP); агент сам определяет активную тему, родителя и **свой код** (без источника обновлений, нестандартное имя) → подтверждение → `project.json` → whitelist.
- **Проверка безопасности до скачивания** (только чтение): `verify-checksums` ядра и плагинов, PHP в `uploads`, вредоносные шаблоны, лишние администраторы, `siteurl`/`home`, `mu-plugins`, drop-in, `.htaccess`, даты изменений (у `wp-config.php` — только дата), Google Safe Browsing / Sucuri SiteCheck. Без SSH — по списку файлов, с пометкой «содержимое не проверено».
  - 🟢 чисто — одна строка, дальше;
  - 🟡 подозрительно — список с пояснениями, ждать решения;
  - 🔴 признаки заражения — стоп, находки, рекомендация (лечение, пароли, что сказать клиенту), ждать решения.
  - «Приостановить» — прогресс с отметкой, при возобновлении проверка повторяется. «Продолжить на риск» — подозрительные файлы не скачивать и не в git, режим заливки `manual`, решение в `DECISIONS.md` и `audit.log`.
  - Отчёт `project-base/security-check.md` — всегда («как было до нас»).
  - Быстрая версия (checksums + PHP в `uploads`) — перед каждой задачей при сверке с сервером.
- **Baseline:** коммит и тег `baseline`; дамп БД остаётся на сервере (персональные данные, GDPR), без SSH — бэкап делает человек.
- **Анализ:** режим, тема, сборка, SCSS, префикс; устаревшие плагины и PHP; свежие ошибки `debug.log`; окружение; данные для этапа 2. Чужие правки и старые ошибки — в отчёт с датой.
- Глубина: доработка / SEO / переезд — короткий; после другого разработчика — полный аудит; редизайн с новой темой — старую тему только читаем. Карта (`project-structure`) — сразу для доработки и аудита.
- Родительская тема и сторонние плагины — скачивание для чтения по запросу, вне git.

### Локальное окружение (сквозное)

Сайт ведёт себя по-разному на серверах → сначала **сравнение окружений** (PHP и модули, лимиты, веб-сервер, версии WP и плагинов, кеш, CDN, `debug.log`), часто решает без переноса.
Перенос: копию делает человек (импорт архива в LocalWP, Duplicator в OSPanel); агент через локальный WP-CLI после «да» — замена домена, почта, кеш, CDN, тестовые ключи Woo, отладка.
Тема связывается junction (`mklink /J`) из репозитория в `wp-content/themes/` локального сайта.
Отдельная команда «перенеси сайт локально» (`project-ops/local.md`); инициализация вызывает её при окружении «локально».
Переносится только код — настройки из локальной админки на прод не уезжают (держать в коде: ACF JSON, `theme.json`).

## Что сейчас разрешено на сервере (справка)

Одинаково для прода и stage. Файлы своего кода — только заливкой из локальных; прямая запись на сервере — запрет (018). Чтение — без подтверждения.
Изменения БД и сайта через WP-CLI — с подтверждением и автодампом (017). Уничтожение данных, `sudo`, прямой ssh — запрет.
